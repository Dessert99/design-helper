# 11. 확정한 값을 실제 코드에 반영하고 확인하는 상황

[상황 목록으로](../flows.ko.md)

## 시작 조건

같은 카드의 블러와 모서리 값이 명시적으로 확정되어 메모에 있다. 프로젝트 코드는 아직 수정하지 않았다. 예시에서는 이 카드의 블러와 모서리가 다른 컴포넌트도 사용하는 공통 토큰에 연결되어 있다고 가정한다.

## 예시 대화와 스킬 행동

> 사용자: 확정한 블러와 모서리 값을 코드에 반영해줘.

1. 메모에서 확정값을 확인한다. 단순한 인상, 언급만 한 대안, 백지 탐색의 출발점을 확정값으로 추가하지 않는다.
2. 실제 파일·줄·토큰과 연결된 사용처를 확인해 영향 범위를 보고한다. 비교 중 표시했던 비용칩의 숫자를 그대로 최종 집계로 사용하지 않는다.
3. 공유 토큰 변경과 이 카드에만 적용하는 변경이 서로 다른 결과를 내는 경우, 반영 범위를 정한다.

> 에이전트: 이 토큰을 바꾸면 다른 사용처도 함께 바뀝니다. 공통 토큰을 수정할까요, 이 카드에만 적용할까요?
>
> 사용자: 이 카드에만 적용해줘.

공통 토큰은 유지하고 이 카드에 확정값을 적용한다. 사용자가 실제 화면을 확인할 수 있도록 변경 위치와 확인할 부분을 안내하며, 시트와 서버는 계속 유지한다.

> 사용자: 실제 화면에서 확인했어. 됐어.

시트와 서버를 유지하던 세션을 종료하고, 스킬이 만든 임시 작업 폴더와 프로세스를 정리한다.

## 끝나는 지점

사용자가 실제 결과를 확인하고 종료를 알린 뒤 임시 자원을 정리하는 데서 끝난다. 코드 반영 승인을 받은 시점에 바로 시트를 없애지 않는다.

프로젝트에 비교용 임시 파일이 남았는지 확인하되, 반영한 코드와 기존 사용자 변경은 보존한다. 원문의 정리 범위 표현에는 [해석이 필요한 부분](limitations.md#정리범위)이 있다.

## 다른 상황과의 차이

[01](01.md)과 [05](05.md)의 확정은 선택 기록이다. 이 상황은 별도 반영 주문을 받아 프로젝트 코드를 바꾸며, 마지막에는 임시 비교 환경까지 정리한다.
