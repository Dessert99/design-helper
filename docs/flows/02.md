# 02. 기존 디자인에 불만은 있지만 무엇을 바꿀지 정하지 못한 상황

[상황 목록으로](../flows.ko.md)

## 시작 조건

기존 버튼이 화면에 있다. 사용자는 답답하다고 느끼지만 비교할 속성을 지정하지 않았다.

## 예시 대화와 스킬 행동

> 사용자: 버튼이 좀 답답해 보여. 다듬고 싶어.
>
> 에이전트: 지금 버튼에서 어느 부분이 답답한가요?
>
> 사용자: 글자가 좌우 테두리에 너무 붙어 있어.
>
> 에이전트: 높이와 글자 스타일은 유지하고, 좌우 여백 차이를 비교해보겠습니다.

먼저 코드와 기존 토큰을 확인하고, 직접 알 수 없는 내용만 한 번에 하나씩 묻는다. 요청이 넓으면 목적·적용 범위·사용 조건 중 시안을 바꾸는 불확실성을 추가로 확인한다. 정해진 질문 목록을 모두 묻는 절차는 아니다. 이 대화로 비교 축은 가로 padding, 유지할 조건은 높이와 글자로 정해졌다.

개수는 사용자 요청과 비교 목적에 맞추며, 탐색 범위가 애매하면 그리기 전에 한 번 묻는다. 그때 프로젝트의 spacing 스케일에서 현재 가로 padding 주변에서 차이를 판단할 수 있는 값을 추려 표본을 그린다. 예를 들어 좌우 padding이 같은 버튼이라면 양쪽을 함께 바꾸고 높이·문구·글자 스타일은 유지한다. 확인과 선택 처리는 [기본 비교 흐름](01.md)을 따른다.

## 끝나는 지점

비교할 속성을 구체화하고 그 속성의 비교 화면을 제공한다. 아직 사용자가 고르지 않았으므로 확정값은 없다.

## 다른 상황과의 차이

[01](01.md)은 속성이 처음부터 명확하다. [03](03.md)은 기존 대상 자체가 없어 불만 대신 필요한 목적·사용 조건을 확인한 뒤 출발점을 그린다.

이 상황에서 에이전트가 `크기 → 여백 → 모서리 → 색` 순서를 정하거나, 답답하다는 말만 듣고 임의로 글자 간격을 선택하면 지침에서 벗어난다.
