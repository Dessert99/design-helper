# design-helper 스킬 패밀리 설계

상태: 0단계 완료, 1차(`design-system`, `design-sync`) 구현과 시험 2회, 1.5차(`design-ux`) 구현과 시험 1회. 2차(`design-brand`, `design-motion`) 구현과 시험 1회(11장, 12장), 3차는 설계안. 2026-11-21 작성, 2026-11-26 갱신.

이 문서는 design-helper를 한 축 비교 도구에서 "디자인 결정을 하나씩 내리게 돕는 스킬 묶음"으로 넓히는 설계다. 구현은 이 문서를 기준으로 하고, 구현 중 바뀐 결정은 이 문서에 먼저 반영한다.

## 1. 이 스킬 묶음이 있어야 하는 이유

### 풀려는 문제

- 디자이너가 아니면 웹페이지 디자인을 어디서부터 정해야 하는지 모른다. 기존 디자인 시스템이 있어도, 새로 시작해도 같다.
- 생성형 디자인 도구(Claude Design 등)는 한 번에 완성된 화면이나 시스템을 내놓는다. 왜 그런 모습인지 알 수 없고, 한 부분을 고치려 하면 다른 부분까지 다시 바뀐다. 그래서 단계적으로 설정하거나 디테일하게 다듬기 어렵다.
- 말로 고르게 하면 판단이 틀린다. "12px이 나을까요, 16px이 나을까요"는 질문이 아니다. 보고 골라야 한다.

### 우리의 답: 결정 루프

모든 스킬은 같은 루프를 돈다. 이 루프가 우리 스킬의 정체성이다.

```
① 결정 하나를 정한다        (값 하나, 규칙 하나, 방향 하나, 패턴 하나)
② 실제 맥락 위에 그린다      (프로젝트 코드, 실제 콘텐츠, 이미 정한 것)
③ 나란히 놓고 차이에 이름을 붙인다
④ 사용자가 눈으로 고른다     (채팅으로, 추천은 근거와 함께 아래에)
⑤ 근거와 함께 기록한다
⑥ 고른 것 위에 다음 결정을 쌓는다
⑦ 반영은 고른 뒤에만 한다    (코드 또는 결정 문서)
```

생성형 도구는 ①~⑥을 건너뛰고 ⑦의 결과물을 한 번에 만든다. 우리는 결과물을 만드는 속도가 아니라, 결과물 안의 결정 하나하나를 사용자가 내리게 하는 데 가치를 둔다.

### 불변 원칙

모든 스킬이 지킨다. 어떤 스킬의 지침이 이 원칙과 부딪히면 지침을 고친다. 원칙에 예외를 만들지 않는다.

| 번호 | 원칙 | 어기는 예 |
|---|---|---|
| P1 | 그려서 보여 준다 | 시안을 산문, 표, ASCII로 설명하고 고르게 한다 |
| P2 | 한 번에 결정 하나 | 로고와 색과 서체를 한 시안 묶음에서 함께 바꾼다 |
| P3 | 차이에 이름을 붙인다 | "A: 모던", "B: 미니멀"처럼 무엇이 다른지 없는 룩 모음(프리셋 갤러리) |
| P4 | 실제 맥락 위에서 그린다 | lorem ipsum, 회색 상자, 실제 화면과 동떨어진 단독 시안 |
| P5 | 결정은 사용자가 한다. 확정은 시안으로 본 것만 | 추천을 시안 위에 두거나, 고르기 전에 하나로 좁힌다. 말로만 들은 값을 확정으로 기록한다 |
| P6 | 보는 것과 반영을 나눈다 | 고르기 전에 프로젝트 코드나 문서를 바꾼다 |
| P7 | 기록이 다음의 기준이다 | 앞에서 정한 값을 무시하고 다음 시안을 그린다 |

P2의 "결정 하나"는 스킬마다 단위가 다르다(2장). 값 하나일 수도, 규칙 하나일 수도, 방향 하나일 수도 있다. 다만 한 시안 묶음 안에서 움직이는 것은 그 하나뿐이고, 그 하나에 이름이 붙어 있어야 한다.

제안의 범위도 스킬마다 다르다. design-helper는 기존 범위를 재는 자로 남고 지어내지 않는다. 나머지 스킬은 안을 제안한다. 하지만 제안하는 스킬도 P2와 P3를 지키므로, 결과는 언제나 "이름 붙은 차이 몇 개 중 하나를 고르는 일"이 된다.

## 2. 스킬별 존재 이유

각 스킬은 "생성형 도구로는 왜 안 되는가"에 답해야 한다. 이 답이 각 `SKILL.md`의 첫 문단이 된다. 답하지 못하는 기능은 만들지 않는다.

| 스킬 | 풀려는 문제 | 결정 단위 | 그리는 것 | 결과물 | 자동 실행 |
|---|---|---|---|---|---|
| `design-helper` | 값 하나를 숫자로는 판단할 수 없다 | 축 하나의 값 | 기존 컴포넌트에 값만 바꾼 사다리 | 코드 반영 | 허용 |
| `design-system` | 어디서 시작할지 모르고, 정할 것이 너무 많다 | 체크리스트 항목 하나 (값보다 규칙) | 대표 화면 보드에 규칙 하나를 바꿔 적용 | 결정 문서 (체크리스트) | 명시적 호출만 |
| `design-sync` | 생성형 도구는 디자인이 바뀌면 화면을 통째로 다시 만든다. 무엇이 바뀌는지 모른 채 받아들이게 된다 | 동기화 범위 하나 (전체, 영역, 항목) | 대표 화면을 지금과 동기화 후로 나란히, 바뀌는 토큰과 영향 범위 | 코드 반영, 프로젝트의 AI 안내 블록 | 명시적 호출만 |
| `design-ux` | UX는 흐름과 동작이라 정지 화면이나 설명으로 판단할 수 없고, 생성형 도구는 한 가지 UX만 낸다 | 패턴 하나 (내비게이션 방식, 입력 흐름, 빈 상태 처리 등) | 실제 콘텐츠로 동작하는 HTML 시안. 같은 과제를 각 안에서 직접 해 보게 한다 | 결정 문서 | 명시적 호출만 |
| `design-motion` | 움직임은 스크린샷이나 설명으로 판단할 수 없고, CSS 근사는 GSAP나 three.js와 다르게 움직인다 | 파라미터 하나 또는 방향 하나 | 실제 라이브러리로 동시에 재생하고 느리게도 보는 시안 | 결정 문서 | 명시적 호출만 |
| `design-brand` | 로고, 아이콘, 캐릭터를 단독 완성품으로 받으면 실제 화면에서 어떻게 보일지 모른다 | 속성 이름이 붙은 방향 하나 | 실제 쓰이는 자리(헤더, 16px 파비콘, 버튼 속 아이콘, 빈 상태 그림)에 입힌 시안 | 결정 문서와 자산 파일 | 명시적 호출만 |

CSS로 할 수 있는 값 하나의 모션(시간, easing)은 지금처럼 `design-helper`가 맡는다. `design-motion`은 라이브러리가 필요한 모션과 3D를 맡는다.

### 스킬 사이의 관계

```
design-system ──(체크리스트와 기초 규칙)──┐
design-ux ────(패턴 결정)────────────────┤
design-brand ─(방향과 자산)───────────────┼──▶ 결정 문서 ──▶ design-helper가 제약으로 읽고
design-motion ─(모션 결정)────────────────┘                    값 하나씩 코드에 반영
                                                  │
                                                  └──▶ design-sync가 확정된 것만 코드에 동기화하고,
                                                       프로젝트의 AGENTS.md와 CLAUDE.md에 안내 블록을 넣음
```

결정 문서가 스킬 사이의 공용 상태다. 어느 스킬이든 문서가 있으면 먼저 읽고, 이미 정한 것 위에 그린다(P7).

## 3. 공통 구조

### 역할 나눔

지금 구조를 그대로 쓴다.

- 메인 에이전트는 스킬의 `SKILL.md`와 `shared/main.md`만 읽는다. 사용자와 worker 사이에서 말을 전하고, 프로젝트와 외부에 쓰는 일을 전부 맡는다.
- worker는 코드를 읽고, 시트를 그리고, 검증한다. 프로젝트 파일과 외부 문서에는 쓰지 않는다. 쓸 것은 블록으로 넘긴다.

### 넘김 블록

worker가 메인에게 넘기는 블록은 세 가지다. 사용자에게는 보이지 않는다.

| 블록 | 언제 | 메인이 하는 일 |
|---|---|---|
| `반영 지시:` | 코드에 반영할 선택을 했을 때 | 코드를 고치고 검증한다 |
| `기록 지시:` | 문서에 기록할 선택을 했을 때 (새로 추가) | 결정 문서에 항목을 쓰고, 스크린샷을 함께 저장한다 |
| `정리 지시:` | 끝날 때 프로젝트에 비교 파일이 남았을 때 | 이번 세션이 만든 근거가 있는 파일만 지운다 |

### 결정 문서

결정 문서의 틀은 Astryx(`meta/astryx`, MIT)가 AI에게 디자인 시스템을 다루게 하는 방식에서 가져온다. 가져오는 것은 틀뿐이다. 문서 구조, 결정 상태, 의도와 값의 분리, 역할로 정리하기, 결정 기록, 다시 볼 조건, 검증 칸이 여기에 해당한다. Astryx의 값, 토큰 이름, 컴포넌트는 가져오지 않는다. 그 값을 쓰고 싶으면 가져오기 출처에서 기반으로 고른다. 문장은 우리 말로 새로 쓰고, README에 참고 출처를 밝힌다.

**위치**

- 사용자가 노션 링크를 주면 그 아래에 같은 구조의 상위, 하위 페이지로 쓴다.
- 언급이 없으면 프로젝트의 `design-decisions/`에 쓴다.
- 노션 링크를 받았는데 노션 도구가 없으면 `design-decisions/`에 쓰고, 그 사실을 한 줄로 알린다.

**구조: 영역마다 파일 하나**

```
design-decisions/
├─ README.md          기반 시스템, 체크리스트 진행 상황, 목차
├─ typography.md      글자
├─ color.md           색
├─ spacing.md         간격과 밀도
├─ shape.md           모서리, 테두리, 그림자
├─ ux-<패턴>.md        UX 결정은 패턴마다 한 파일
└─ assets/            결정의 근거가 된 시트 스크린샷
```

영역을 나누면 한 영역만 다시 정할 때 그 파일만 읽으면 된다. 전체 진행 상황은 `README.md`의 체크리스트 한 곳에서 본다.

**기록 하나의 양식** (`shared/decisions.md`에 둔다)

| 칸 | 내용 | 가져온 방법 |
|---|---|---|
| frontmatter `status` | `초안`, `확정`, `보류`, `보관` 중 하나 | 결정 상태 (draft, current, archived) |
| frontmatter `decided` | 확정한 날짜 | 승인 날짜 |
| frontmatter `base` | 이어받은 기반과 버전. 없으면 비운다 | 상속과 덮어쓰기 (`extends`) |
| frontmatter `reopen_when` | 무엇이 바뀌면 이 문서를 다시 봐야 하는가 | 다시 볼 조건 (`review_triggers`) |
| frontmatter `verify` | 이 결정이 지켜지는지 무엇으로 확인하는가 | 검증 방법 (`verified_by`) |
| 의도 | "~해야 한다" 문장. 숫자를 쓰지 않는다. 사용자의 "느낌"이 여기로 온다 | 의도와 값의 분리 (design spec) |
| 역할과 값 | 역할, 토큰, 값(라이트와 다크), 출처(기반 그대로, 시안 글자) | 역할 기반 토큰 |
| 결정 기록 | 번호(D1), 결정한 사람과 날짜, 시트 요청과 시안 글자, 이유, 스크린샷 | 결정 로그 (DEC-n) |
| 스크린샷 설명 | 상태, 모드, 폭, 보여 주는 결정 | 기준 이미지의 맥락 |
| 열린 질문 | 아직 못 정한 것 (Q1). 체크리스트의 보류 항목과 연결한다 | 열린 질문 (OQ-n) |
| 정하지 않는 것 | 이 문서가 다루지 않고 다른 문서에 맡기는 것 | 내용 경계 (Content boundary) |

frontmatter 이름은 에이전트가 안정적으로 읽도록 영어로 쓰고, 값과 본문은 한국어로 쓴다.

**규칙**

1. **확정은 시각 자료를 보고 고른 것만.** 디자인 시스템의 값을 새로 정하든 고치든, 결정은 반드시 시트에 그린 시안을 보고 채팅에서 고른 것이어야 한다. 사용자가 숫자를 직접 말해도(`버튼은 8px로 둥글게`) 그 값을 시트에 그려 보여 주고, 그동안은 `초안`으로 둔다. 비교 대상이 필요하면 현재 값이나 이웃 단계를 함께 그린다. 기반을 고를 때도, 결정을 되돌릴 때도 같다.
2. **확정의 길은 하나다.** 코드에 이미 들어갔다거나 반대가 없었다는 이유로 확정으로 보지 않는다.
3. **바꿀 때는 지우지 않고 보관한다.** 옛 결정은 `보관`으로 남기고 새 결정과 서로 링크한다.
4. **역할 이름의 우선순위.** 프로젝트에 이미 있는 토큰 이름, 사용자가 정한 이름, 스킬의 기본 역할 목록 순서로 쓴다. 기본 목록은 출발점일 뿐이고, 역할을 바꾸거나 더하는 것도 체크리스트 항목이다.
5. **역할 먼저, 값은 나중에.** 영역마다 역할을 먼저 정하고, 역할마다 값을 사다리로 고른다.
6. **문서와 코드가 다르면 문서의 `확정`이 기준이다.** 다른 점은 발견 사항으로 알리고 자동으로 고치지 않는다. 문서가 없는 기존 프로젝트에서 시작할 때는 현재 코드 값을 `초안`으로 불러와 출발점으로 쓴다.
7. **`design-system`은 코드를 고치지 않는다.** 결과물은 결정 문서뿐이다. 코드에 옮기는 일은 사용자가 따로 요청할 때 design-helper로 하나씩, 또는 이후에 만들 적용 단계에서 한다.
8. **design-helper도 문서를 지킨다.** 결정 문서가 있으면 읽고 제약으로 쓴다. 고른 값이 문서에 기록된 역할에 해당하면 `반영 지시:`와 함께 `기록 지시:`도 넘긴다. 문서가 없으면 지금과 같다.
9. **기반은 버전과 함께 기록하고 저절로 따라가지 않는다.** 기반을 바꾸는 것은 새 결정이고, 규칙 1에 따라 시트로 본다.
10. **연쇄 확인.** 결정이 바뀌면 그 변화와 `reopen_when`이 겹치는 다른 문서를 찾아 알린다. 다시 정할 때는 규칙 1에 따라 시트로 보여 준다. 자동으로 고치지 않는다.
11. **측정할 수 있는 것은 측정한다.** 대비, 넘침, 잘림은 직접 확인해 캡션에 적는다. 사용자에게는 취향과 방향만 한 번에 하나씩 묻는다. (`shared/core.md`)
12. **새로 만들기 전에 찾는다.** 새 토큰이나 결정을 제안하기 전에 결정 문서와 프로젝트 토큰을 먼저 찾는다. 새로 만들 때는 기존 것을 못 쓰는 이유를 캡션에 적는다. (`shared/core.md`)
13. **반영 후 자기 점검.** 코드에 반영한 뒤, 바뀐 줄에 결정된 토큰 대신 하드코딩된 색이나 px가 들어갔는지 검사해 보고한다. (`shared/main.md`)

**한 번의 결정이 기록되는 흐름**

```
사용자: "C로 갈게"
  → worker: 기록 지시: (어느 문서의 어느 칸에 무엇을, 스크린샷 경로)
  → 메인: 해당 영역 문서에 결정과 값을 쓰고, 스크린샷을 assets/로 복사하고, README 체크리스트를 갱신
  → 메인: reopen_when이 겹치는 문서를 한 줄로 안내
```

### 가져오기

값을 처음부터 고르는 대신, 공개된 디자인 시스템의 값을 시안 후보로 가져올 수 있다.

- **출처:** Tailwind 기본값, Radix Colors, Open Props, Material 3, shadcn/ui. 값이 공개돼 있고 가져다 써도 되는 라이선스인 것만 둔다. 이 밖의 시스템은 사용자가 이름을 말할 때만 쓰고, 회사의 브랜드 시스템은 값을 참고하는 데만 쓴다.
- **단위:** 항목 하나(간격 기본 단위만), 영역 하나(색 전체), 전체 기반(`base`) 중 고른다. 섞어 써도 된다.
- **가져오는 것:** 디자인 토큰(값과 역할 구분 방식)만 가져온다. UI 컴포넌트는 코드가 아니라 모양의 값(높이, 여백, 모서리)만 후보로 쓴다. 접근성은 가져오는 대상이 아니라 우리가 재는 기준이다.
- 가져온 값도 시안 후보 중 하나다. 지금까지 정한 것이 모두 적용된 보드 위에서 비교하고, 고른 것만 확정한다(규칙 1).

### 접근성

두 층으로 나눈다.

| 층 | 내용 | 다루는 곳 |
|---|---|---|
| 보이는 접근성 | 글자와 배경의 대비, 누르는 영역 크기, 포커스 표시, 색만으로 의미를 전하지 않기, 움직임 줄이기 | `design-system`. 기준은 WCAG 2.2 AA(본문 대비 4.5:1, 큰 글자와 아이콘 3:1, 누르는 영역 약 44px). 직접 재서 캡션에 적고, 기준 미달 시안도 숨기지 않고 표시한다(`대비 부족 2.5:1`). 포커스 표시 모양은 결정 항목 하나로 두고 시안으로 고른다 |
| 동작 접근성 | 키보드 이동, 포커스 가두기, 스크린리더용 정보(ARIA) | 결정 문서의 "구현 방침"으로 기록한다. 프로젝트 스택에 맞는 후보를 제안하고 사용자가 고른다(React면 Radix Primitives나 Base UI, 단순한 화면이면 HTML 기본 요소 우선). 라이브러리 설치와 적용은 코드를 고치는 단계의 일이다 |

### AI가 결정을 따르게 하는 장치

결정 문서를 만들어도 다른 AI 세션이 그것을 모르면 소용이 없다. Astryx(`meta/astryx`)가 AI에게 자기 디자인 시스템을 따르게 하는 방식에서 장치만 빌려 와, 우리 결정 문서에 맞게 새로 쓴다. Astryx의 문서나 값은 가져오지 않는다.

| 장치 | Astryx | 우리 |
|---|---|---|
| 안내문 심기 | `astryx init`이 프로젝트의 `AGENTS.md`, `CLAUDE.md`에 안내 블록을 쓴다 | `design-sync`가 같은 두 파일에 표시 주석으로 감싼 안내 블록을 넣는다. 우리 스킬을 쓰지 않는 평범한 코딩 세션도 결정을 따르게 된다 |
| 추측 대신 확인 | 컴포넌트를 쓰기 전에 CLI로 확인하게 한다 | 화면을 만들기 전에 결정 문서의 해당 영역을 읽게 한다. 확정 값만 쓰고, 정해지지 않은 것은 지어내지 않고 가장 가까운 토큰을 쓴 뒤 알린다 |
| 내기 전 점검 | 하드코딩된 색과 px를 토큰으로 바꾸게 한다 | 같은 점검을 안내 블록에 넣는다 |
| 바꾸는 길 막기 | (해당 없음) | 결정된 값을 코드나 문서에서 직접 바꾸지 못하게 하고, 시안을 거치는 `design-system`으로 안내한다 |

- 이 장치는 결정 문서 양식과 분리해 `shared/agent-guide.md` 한 파일에 둔다. 안내 블록의 원본, 넣고 갱신하는 규칙, 점검 규칙이 여기에 모인다.
- 블록은 표시 주석(`<!-- DESIGN-DECISIONS:START -->`, `END`) 사이만 관리한다. 다시 동기화하면 그 사이만 바뀌고, 사용자가 쓴 나머지는 건드리지 않는다.
- 두 파일은 그 프로젝트의 모든 AI 세션에 영향을 주므로, 처음 넣을 때 한 번 확인을 받는다.
- 동기화로 코드와 문서가 맞춰진 시점에 넣는다. 문서에만 있고 코드에 없는 값을 다른 AI가 먼저 쓰지 않게 하기 위해서다.

### 동기화 (`design-sync`)

```
① 결정 문서에서 확정 항목만 읽음 (초안, 보류는 건너뜀)
② 프로젝트의 스타일 체계를 감지하고 지금 토큰과 비교 (추가, 변경, 같음, 코드에만 있음)
③ 바뀌는 토큰마다 영향 범위 계산
④ 시트에 대표 화면을 지금과 동기화 후로 나란히 그림
⑤ 사용자가 보고 범위를 고름 (전체, 영역, 항목)
⑥ 메인이 코드에 반영하고 검증하고, 하드코딩 값을 점검하고, 안내 블록을 넣거나 갱신
```

- 방향은 문서에서 코드로만 간다. 코드 값을 문서로 가져오는 것은 `design-system`이 처음 시작할 때 초안으로 한다(규칙 6).
- 동기화 중에 코드 값이 낫다고 판단되면 문서를 고쳐야 하고, 그 변경은 `design-system`에서 시안으로 정한다.
- 결과물 형식은 프로젝트의 스타일 체계를 따른다(CSS 변수, Tailwind 테마, SCSS 변수, CSS-in-JS 테마). 감지는 `shared/stylesystems.md`를 쓴다.

### 작업 폴더와 키트

지금과 같다. 시트, 서버, 메모, 스크린샷은 프로젝트 밖의 `$WS`에 둔다. 서버(`serve.py`), 시트(`sheet.html`), 검사(`check.cjs`)는 모든 스킬이 함께 쓴다.

- 스킬 폴더에는 그 스킬의 규칙만 둔다. 두 스킬 이상이 쓰는 규칙은 `shared/`로 올린다. 같은 규칙을 두 곳에 쓰지 않는다.
- 아직 구현하지 않은 스킬은 폴더도 만들지 않는다. 동작하지 않는 명령어가 목록에 보이지 않게 한다.

## 5. Claude Code와 Codex 양쪽 지원

### 플랫폼별 차이

| 항목 | Claude Code | Codex |
|---|---|---|
| 설치 | `.claude-plugin/plugin.json` | `.codex-plugin/plugin.json`, `"skills": "./skills/"` |
| 명령어 | `/design-helper:design-system` (플러그인 이름이 앞에 붙음) | `$design-system` |
| 자동 실행 끄기 | `SKILL.md` frontmatter `disable-model-invocation: true`. description이 맥락에 아예 들어가지 않는다 | 스킬의 `agents/openai.yaml`에 `policy.allow_implicit_invocation: false` |
| worker 띄우기 | Agent 도구, subagent type `design-helper:worker` | `spawn_agent`, 독립 맥락 (`fork_turns: "none"` 또는 `fork_context: false`) |
| worker에 이어 말하기 | `SendMessage` | `send_input` 또는 `followup_task`, 기다릴 때 `wait_agent`, 끝낼 때 `close_agent` |
| 공용 폴더 경로 | `${CLAUDE_PLUGIN_ROOT}/shared/` (스킬과 에이전트 본문에서 치환됨. `../`는 보장되지 않음) | 스킬 폴더 기준 `../../shared/` (공식 `work-pets` 플러그인과 같은 방식) |
| 스킬 자신의 폴더 | `${CLAUDE_SKILL_DIR}` | 스킬을 불러올 때 주어지는 경로 |
| 이미지 생성 | 없음 | 내장 `image_gen` (`imagegen` 시스템 스킬) |
| 노션 | 연결된 Notion 도구 | 설치된 Notion 플러그인 |
| 패키징 제외 | 없음 | `.codexignore`가 `agents/`, `docs/`, `scripts/`를 뺀다 |

### 양쪽에서 같은 파일이 동작하게 하는 규칙

1. **경로는 두 가지를 함께 적는다.** 예: "공용 파일은 플러그인 최상위의 `shared/`에 있다. Claude Code에서는 `${CLAUDE_PLUGIN_ROOT}/shared/`, Codex에서는 이 스킬 폴더 기준 `../../shared/`다." Codex에서는 변수가 치환되지 않고 글자 그대로 남으므로, 두 번째 경로를 쓰라고 적어 둔다.
2. **도구는 플랫폼 이름보다 능력으로 적는다.** 예: "이미지 생성 도구가 있으면 쓰고, 없으면 SVG로 그리고 그 사실을 시트에 적는다." 플랫폼이 바뀌거나 도구가 늘어도 지침을 고칠 필요가 없다.
3. **도구 이름이 꼭 필요한 곳(worker 띄우기, 이어 말하기)은 `shared/main.md` 한 곳에만 둔다.** 플랫폼 도구가 바뀌면 그 파일만 고친다.
4. **worker 에이전트는 하나다.** Claude Code의 `agents/worker.md`는 첫 메시지로 받은 스킬의 `worker.md` 경로를 읽고 따른다. Codex는 `agents/`를 패키징하지 않으므로, 메인이 처음부터 `worker.md`의 절대 경로를 넘긴다(지금 방식).
5. **새 스킬마다 양쪽 자동 실행 설정을 함께 넣는다.** `disable-model-invocation`과 `agents/openai.yaml`은 짝으로 다닌다. 한쪽만 넣으면 다른 플랫폼에서 무거운 스킬이 자동 실행된다.

### 쓰지 않기로 한 것

- Claude Code의 `context: fork` (스킬을 포크된 서브에이전트로 한 번 실행): 결과를 한 번 받고 끝나서, 여러 라운드 이어지는 비교에 맞지 않는다. 지금처럼 worker를 띄우고 이어 말하는 방식을 유지한다.
- 접두사 없는 Claude Code 명령어(`/design-system`): 문서에서 확인되지 않아 기대하지 않는다. README에는 `/design-helper:design-system`으로 안내한다.

## 6. 잘못된 채택 막기

| 겹 | 장치 |
|---|---|
| 1 | 자동 실행은 `design-helper` 하나만 허용한다. 나머지는 양쪽 플랫폼 모두 명시적 호출로만 실행된다 |
| 2 | `design-helper`의 description에 제외 문구를 넣는다: 디자인 시스템, UX 패턴, 브랜드, 라이브러리 모션 작업에는 쓰지 않는다 |
| 3 | `design-helper`에 그런 요청이 들어오면 혼자 범위를 넓히지 않는다. 맞는 명령어를 한 줄로 안내하고, 지금 할 수 있는 한 축 비교를 제안한다 |
| 4 | 명시적으로 부른 스킬 안에서도 범위가 애매하면 `shared/clarification.md`대로 한 번 묻는다 |

채택 확인용 프롬프트 목록을 `docs/`에 두고, 지침을 바꿀 때마다 기대한 스킬이 채택되는지 손으로 확인한다.

| 프롬프트 | 기대 |
|---|---|
| 카드 그림자 블러 5가지로 보여줘 | `design-helper` |
| 버튼 여백 12랑 16 중에 뭐가 나아 | `design-helper` |
| 디자인 시스템 처음부터 잡고 싶어 | 자동 채택 없음. `design-helper`가 채택되면 `/design-helper:design-system`(Codex는 `$design-system`) 안내 |
| 로고 만들어줘 | 자동 채택 없음. `design-helper`가 채택되면 `design-brand` 안내 |
| 카드 등장 애니메이션을 GSAP로 순서 있게 | 자동 채택 없음. `design-helper`가 채택되면 `design-motion` 안내 |
| 버튼 hover 전환 시간 비교해줘 | `design-helper` |
| 디자인 문서대로 코드 맞춰줘 | 자동 채택 없음. `design-sync` 안내 |
| 이 버튼 컴포넌트 구현해줘 | 채택 없음 (평범한 코딩) |

| 3차 | three.js, 캐릭터 | 이미지 생성 도구 사용 방식을 정한 뒤 진행 |

## 8. 아직 정하지 않은 것

- 캐릭터와 일러스트에서 이미지 생성 도구를 쓸지, Claude Code처럼 도구가 없는 환경에서는 어디까지 할지

## 9. 정해진 것 (1차)

- 기본 체크리스트: 필수는 기반, 글자, 간격, 색, 모양, 구현 방침. 선택은 레이아웃, 모션, 컴포넌트. 필수를 마치면 선택 영역을 이어 갈지 한 번 묻는다. 항목, 기본 역할, 기본 의도, 기본 검사는 `skills/design-system/references/checklist.md`.
- 진행 상황: 시트 목차 위에 영역별로 정한 수와 보류 수를 표시한다(`shared/sheet.md`, Checklist progress).
- 대비와 누르는 영역 크기는 `check.cjs --a11y`로 잰다. 실제로 계산된 글자색과, 뒤에 겹친 배경색을 합성한 색으로 WCAG 대비를 구한다.
- 두 플랫폼이 같은 `SKILL.md`를 쓴다. Codex는 `disable-model-invocation` 항목이 있어도 스킬을 불러온다(2026-11-25 실험으로 확인).


## 10. design-ux 설계 (1.5차, 초안)

### 존재 이유

UX는 흐름과 동작이다. 같은 화면이라도 "취소 요청 주문을 찾아 처리하는" 과제를 몇 번의 클릭으로, 어떤 순서로, 어디서 길을 잃으며 하게 되는지가 다르다. 정지 화면이나 설명으로는 이 차이를 판단할 수 없다. 생성형 도구는 그중 한 가지 흐름만 만들어 내고, 사용자는 다른 흐름이 있었는지도 모른 채 받아들인다. design-ux는 UX 디자이너가 일하는 순서를 따라, **같은 과제를 여러 흐름으로 직접 해 보고 고르게** 한다.

### 근거로 삼은 작업 방식

- **Double Diamond** (Design Council): 문제를 넓게 본 뒤 정의하고(발견, 정의), 해법을 넓게 낸 뒤 좁힌다(전개, 전달). 발산과 수렴을 번갈아 한다.
- **과제 분석과 사용자 흐름** (Nielsen Norman Group): 과제는 시작과 끝이 있는 관찰 가능한 활동이다. 단계와 갈림길로 나누고, 흐름은 과제를 이루는 화면 경로(wireflow)로 그린다.
- **과제 시나리오와 평가** (NN/g의 사용성 시험, Nielsen의 10가지 원칙, 인지적 워크스루): 목표에서 나온 시나리오로 시안을 시험하고, 단계마다 사용자가 다음 행동을 알아챌 수 있는지 본다.
- **화면 상태 점검** (`ghaida/intent`의 `fortify`, CC0): 정상 상태만 그리지 않고 빈 상태, 불러오는 중, 오류 같은 상태를 빠짐없이 본다.

가져오는 것은 순서와 방법이다. 문장이나 목록은 우리 말로 새로 쓴다.

### 흐름: 과제 하나를 거친 것에서 세밀한 것으로

UX 디자이너는 큰 구조를 먼저 정하고 세부로 내려간다. 흐름이 정해지기 전에 버튼 모양을 고르지 않는다. design-ux도 과제마다 아래 순서를 따른다. 각 단계는 결정 하나이고, 1, 2는 대화로, 3 이후는 시트로 정한다.

| 단계 | 하는 일 | 정하는 방법 |
|---|---|---|
| 1. 목표와 사용자 | 누가, 어떤 상황에서, 무엇을 끝내려 하나. 코드에서 추론해 한 줄로 말하고 빠진 것만 묻는다 | 대화 |
| 2. 과제 분석 | 과제를 시작과 끝, 단계, 갈림길로 나눈다. 지금 코드의 흐름을 Playwright로 실제로 따라가 단계 수와 막히는 곳을 잰다(인지적 워크스루) | 대화. 지금 흐름의 단계 띠를 함께 보여 준다 |
| 3. 흐름 | 과제가 몇 개의 화면을 거치나, 어디서 시작해 어디서 끝나나 (한 화면에서 처리, 상세로 갔다가 돌아옴, 단계별 마법사 등) | 시트 |
| 4. 화면 구성 | 흐름 안 핵심 화면에서 무엇을 먼저 보여 주나 (정보의 순서와 묶음) | 시트 |
| 5. 상호작용 패턴 | 단계마다의 방식 (상세는 모달, 패널, 새 페이지 / 확인은 확인 창, 되돌리기 알림 / 검색은 즉시, 버튼) | 시트, 패턴 하나씩 |
| 6. 상태 | 고른 흐름의 빈 상태, 불러오는 중, 오류, 일부만 성공, 데이터 많음, 긴 글, 권한 없음, 처음 쓰는 사람 | 시트, 상태마다 |
| 7. 문구 | 버튼 이름, 확인 문구, 오류와 빈 상태 안내 | 시트 |

모든 단계를 다 할 필요는 없다. 사용자가 고른 단계부터 시작할 수 있고, 건너뛴 단계는 기록에 `보류`로 남는다.

### 그리는 것: 동작하는 시안과 단계 띠

- **동작하는 시안:** 실제 프로젝트 CSS와 결정 기록의 확정 값으로 만든 보드(`shared/board.md`) 위에, 흐름이나 패턴만 다르게 동작하는 HTML 시안을 만든다. 데이터는 같은 실제 데이터다. 사용자가 직접 눌러 볼 수 있다.
- **단계 띠:** NN/g의 wireflow를 동작하는 시안으로 만든 것이다. Playwright가 과제 시나리오를 실제로 수행하며 단계마다 화면을 찍고, 시안 아래에 가로로 늘어놓는다. 눌러 보지 않아도 흐름을 나란히 비교할 수 있고, 시안이 정말 그렇게 동작한다는 검증도 된다.
- **조건:** 패턴이 달라지는 조건만 함께 그린다(데이터 많음, 빈 상태 등). 맥락 규칙과 같은 원칙이다.
- 동작은 시안용 스크립트로 흉내 낸다. 모든 시안에 `실물과 다름`을 한 번 적는다.

### 재고 평가하는 것

시트의 캡션은 단계 띠를 만들며 잰 값과, 단계마다의 워크스루 결과를 적는다.

| 항목 | 예 |
|---|---|
| 클릭과 입력 수, 화면 전환 수 | `클릭 3 · 입력 1 · 전환 0` |
| 목록 위치 유지 | 상세를 닫은 뒤 스크롤 위치가 남는지 |
| 키보드만으로 완료 | Tab과 Enter로 끝낼 수 있는지, 포커스가 어디로 가는지 |
| 워크스루 | 단계마다 "다음에 할 일이 보이나, 누른 뒤 결과를 알 수 있나". 막히는 단계를 적는다 (`2단계: 취소 버튼이 메뉴 안에 숨어 있음`) |
| 원칙 위반 | Nielsen의 10가지 원칙 중 걸리는 것만, 단계와 함께 (`되돌릴 수 없음: 취소 즉시 확정`) |

측정은 사실이고, 워크스루와 원칙은 판단이다. 캡션에서 둘을 구분해 적는다. 어느 쪽이든 문제가 있는 시안을 숨기지 않는다.

### 결과물

- 결정 기록의 `ux-<과제>.md`: 목표와 사용자, 과제 단계, 의도, 단계별로 고른 흐름과 패턴과 상태와 문구, 측정값, 단계 띠 스크린샷, 그리고 **완료 조건**(이 과제가 성공했다고 볼 수 있는 조건. 구현 뒤 같은 시나리오로 확인할 수 있다).
- **코드는 쓰지 않는다.** 구현은 평범한 코딩으로 하고, 안내 블록이 AI에게 `ux-*.md`를 읽고 따르게 한다.

### 다른 스킬과의 관계

- 혼자 쓸 수 있다. 결정 기록에 시각 결정이 있으면 그 값으로, 없으면 지금 코드의 모습으로 그린다.
- 동작 접근성 방침이 기록에 있으면 시안의 키보드 동작을 그 방침에 맞춘다.
- 명시적 호출만 허용한다.

### 범위와 정한 것

- 기능 하나(과제 하나) 단위다. 요청이 좁으면 해당 단계부터 시작하고, 1, 2단계는 추론해 한 줄로 말한다. 앱 전체의 메뉴 구조, 사이트맵, 기능을 넘나드는 여정은 다루지 않는다.
- 결과물은 기록만 남긴다. 단계 띠를 기본으로 넣는다. 1~7단계 순서로 간다.
- 단계 띠는 키트의 `walk.cjs`가 만든다. 시안에서 과제를 실제로 수행하며 단계마다 찍고, 클릭, 입력, 화면 전환, 목록 위치, 키보드만으로 완료 여부를 잰다.
- 스킬 독립성: 안내 블록은 어느 스킬이든 기록을 처음 쓸 때 넣는다(처음 한 번 확인). README는 최소 양식으로 시작하고, 체크리스트는 design-system을 쓸 때만 생긴다.


## 11. design-brand 설계 (2차)

### 존재 이유

로고와 아이콘은 쓰이는 자리에서 판단해야 한다. 같은 로고도 넓은 헤더에서는 멀쩡하다. 그런데 16px 파비콘에서는 뭉개지고, 360px 모바일 헤더에서는 메뉴 버튼과 부딪힌다. 아이콘 세트도 단독 목록에서는 다 깔끔해 보인다. 하지만 글자 붙은 버튼 안의 16px, 표의 행 동작, 빈 상태 그림에 넣으면 굵기와 인상이 확연히 다르다. 생성형 도구는 로고를 흰 바탕 위의 완성 이미지 한 장으로 낸다. 작은 크기 판도 없고, 한 속성만 고치려 해도 전체가 다시 그려진다. 기존 브랜드와 닮았는지도 알 수 없다. design-brand는 브랜드 디자이너의 순서를 따른다. **바탕을 정하고, 방향을 넓게 낸 뒤, 결정 하나씩 실제 쓰이는 자리에 입혀 고르게** 한다.

### 근거로 삼은 작업 방식

- **브랜드 아이덴티티 작업 순서** (로고 디자인 실무 글 여러 곳의 공통 순서): 브리프로 이름, 성격, 쓰일 자리를 정한다(발견). 여러 방향을 거칠게 낸다(스케치). 하나를 골라 벡터로 다듬는다. 실제 쓰이는 자리에 놓고 흑백, 단색, 작은 크기로 시험한다(적용 시험).
- **반응형 로고 체계** (Smashing Magazine, Viget의 반응형 로고 글): 로고를 전체, 간단, 아이콘의 단계로 나눈다. 작은 단계일수록 가는 선, 그러데이션, 작은 장식을 뺀다. 최소 크기는 정해진 숫자가 아니라 실제 화면에서 시험해 정한다. 밝은 바탕, 어두운 바탕, 단색에서 모두 성립해야 한다.
- **1초 인식 시험**: 비슷한 표식들 사이에 잠깐 놓고 구별되는지 본다. 단순화하다 흔한 모양이 되면 되돌린다.
- **아이콘 체계**: 한 세트 안에서 격자(대개 24px), 획 두께, 모서리, 채움 방식이 맞는다. 세트를 섞지 않는다. 크기마다 획이 화면 픽셀에 어떻게 떨어지는지가 선명함을 정한다.

가져오는 것은 순서와 방법이다. 문장은 우리 말로 새로 쓴다.

### 흐름: 바탕 하나, 갈래 둘

바탕(1단계)을 대화로 정한 뒤 아이콘 갈래와 로고 갈래로 나뉜다. 두 갈래는 서로를 전제로 하지 않는다. 사용자가 고른 갈래부터 시작하고, 한쪽만 해도 된다. 각 갈래 안에서는 큰 것에서 작은 것 순서로 간다.

| 단계 | 하는 일 | 정하는 방법 |
|---|---|---|
| 1. 바탕 | 이름, 무엇을 하는 제품인지, 성격 단어 세 개, 쓰일 자리, 닮으면 안 되는 브랜드. 코드와 기록에서 추론해 한 줄씩 말하고 빠진 것만 묻는다 | 대화 |
| **아이콘 갈래** | | |
| I2. 세트 | 공개 세트 2~4개 중 하나 (Lucide, Phosphor, Tabler, Heroicons, Material Symbols). 지금 코드에 세트가 있으면 `A 지금` | 시트 |
| I3. 굵기와 채움 | 획 두께(1.5, 2) 또는 세트의 굵기 단계, 선택된 상태에서 채움으로 바꿀지 | 시트 |
| I4. 크기 | 자리마다의 크기(글자 옆 16, 버튼 20, 메뉴 24 등)와 글자와의 줄 맞춤 | 시트 |
| I5. 개념별 그림 | 뜻이 갈리는 개념만 하나씩 (설정: 톱니바퀴 또는 조절기, 내보내기: 화살표 또는 상자) | 시트, 개념 하나씩 |
| **로고 갈래** | | |
| L2. 형식 | 글자형, 머리글자형, 심볼형, 조합형 | 시트 |
| L3. 서체 | 이름 글자의 서체. 프로젝트에 이미 있는 서체 먼저, 그다음 공개 라이선스(OFL 등) 서체 | 시트 |
| L4. 심볼 방향 | 심볼형이나 조합형일 때. 방향마다 속성 이름을 붙인다(머리글자 변형, 기하 도형, 제품이 하는 일의 은유) | 시트 |
| L5. 세부 | 굵기, 자간, 모서리, 심볼과 글자의 비율. 한 번에 하나 | 시트, 속성 하나씩 |
| L6. 작은 크기 판 | 16px과 32px에서 쓸 단순화한 판. 전체 판에서 무엇을 뺄지 | 시트 |

- **아직 정하지 않은 단계는 가장 평범하게 고정한다.** L2에서 형식을 비교할 때 서체는 프로젝트 본문 서체, 심볼은 기본 도형 하나로 모든 시안에 같게 둔다. design-ux의 "고정한 것" 규칙과 같고, 섹션 설명에 한 번 적는다.
- **색은 정하지 않는다.** 결정 기록의 주 색이 `확정`이면 그 색으로 그린다. 없으면 검정 단색으로 그린다. 로고 실무도 흑백에서 먼저 성립하는지를 본다. 단색 판과 반전 판(어두운 바탕)은 고르는 대상이 아니라 재는 대상이다.

### 그리는 것: 쓰이는 자리 보드

각 시안은 한 장의 "쓰이는 자리 보드"다. 프로젝트의 실제 CSS로 만든 보드(`shared/board.md`)에 아래 자리를 실제 크기로 놓는다. 프로젝트에 없는 자리(앱 아이콘 등)는 바탕에서 말한 쓰일 자리만 넣는다.

| 갈래 | 자리 |
|---|---|
| 로고 | 데스크톱 헤더, 360px 모바일 헤더(메뉴 버튼과 함께), 브라우저 탭의 16px 파비콘, 32px 파비콘, 180px 앱 아이콘, 원형 프로필 사진, 어두운 바닥글 |
| 아이콘 | 왼쪽 메뉴(24), 글자 붙은 버튼(16~20), 아이콘만 있는 버튼, 표의 행 동작, 상태 표시, 빈 상태 그림(48 이상) |

- **아이콘은 지금 코드의 개념 목록으로 그린다.** 코드에서 쓰는 아이콘을 개념으로 모으고(설정, 삭제, 검색...), 각 세트에서 같은 개념을 찾아 같은 자리에 놓는다. 세트에 없는 개념은 빈칸으로 두고 `없음`이라고 적는다. 지어내지 않는다.
- **로고는 SVG로 그린다.** 글자는 실제 서체 파일로 그리고, 확정할 때 글자를 윤곽선으로 바꾼 판을 함께 만든다.
- **16px은 확대해서도 보여 준다.** 실제 크기 옆에 픽셀 그대로 8배로 키운 그림을 둔다. 어디가 뭉개지는지 눈으로 보이게 하기 위해서다.

### 재고 판단하는 것

| 항목 | 예 | 구분 |
|---|---|---|
| 작은 크기 선명도 | 16px에서 반쯤 칠해진 픽셀 비율 `흐린 픽셀 38%`, 가장 가는 획의 화면 두께 `0.7px` | 측정 |
| 헤더 폭 | 360px 헤더에서 로고가 차지하는 폭, 메뉴 버튼과의 간격 | 측정 |
| 대비 | 로고와 아이콘이 바탕과 3:1 이상인지 (`check.cjs --a11y`) | 측정 |
| 아이콘 세트 | 필요한 개념 중 없는 수, 실제 렌더된 획 두께, 라이선스, 버전 | 측정 |
| 흔한 모양 | 체크, 번개, 잎, 말풍선, 지구본처럼 흔한 모양에 기대는지. 1초 인식 시험의 결과 | 판단 |
| 닮은 브랜드 | 바탕에서 말한 브랜드와 닮았는지 | 판단 |

측정은 사실이고, 흔한 모양과 닮음은 판단이다. 캡션에서 둘을 구분한다. **모든 로고 시안에는 `상표 검색 안 함` 표시가 붙는다.** 상표 검색(한국은 KIPRIS)은 사람이 하고, 기록의 `verify`에 남긴다.

### 비슷한 로고를 만들지 않는 규칙

- 기존 브랜드를 기준으로 그리지 않는다. "토스 같은 느낌"은 속성(`굵은 둥근 글자`, `밝은 파랑`)으로 바꿔 말하고, 그 속성으로만 그린다.
- 바탕에서 말한 닮으면 안 되는 브랜드와 같은 업종의 대표 로고를 머릿속 기준으로 두고, 형식과 모양이 겹치는 안은 내지 않는다.
- 사용자가 특정 브랜드를 따라 해 달라고 하면 하지 않는다고 한 줄로 말하고, 그 브랜드에서 좋다고 느낀 속성을 묻는다.
- 서체를 고치지 않은 글자형 로고는 상표로 보호받기 약하다. 해당하는 시안의 캡션에 한 번 적는다.

### 이미지 생성 도구

로고와 아이콘 후보는 SVG로만 그린다. 이미지 생성 도구가 있어도 쓰지 않는다. 래스터 그림은 16px 판을 만들 수 없고, 속성 하나만 바꿔 다시 그릴 수 없다. 그래서 P2를 지킬 수 없다. 캐릭터와 일러스트(3차)에서 쓰는 방식을 따로 정한다.

### 결과물

- 결정 기록에 `icons.md`와 `logo.md` 두 영역 파일을 쓴다. 같은 양식(`shared/decisions.md`)을 따른다.
  - `icons.md`: 세트 이름과 버전과 라이선스, 굵기, 자리별 크기, **개념과 아이콘 이름의 대응표**(개념, 세트의 아이콘 이름, 쓰는 곳). 다른 AI가 아이콘을 지어내지 않고 이 표에서 고르게 한다.
  - `logo.md`: 형식, 서체와 라이선스, 단계별 판(전체, 간단, 아이콘)과 각 판의 최소 크기, 여백 규칙, 단색과 반전 판이 성립하는지.
- 자산 파일은 `design-decisions/assets/brand/`에 둔다: `logo.svg`, `logo-mark.svg`, `logo-small.svg`, `favicon.svg`, 그리고 키트가 뽑은 `favicon-32.png`, `apple-touch-icon.png`(180).
- **코드는 쓰지 않는다.** 아이콘 패키지 교체와 파비콘 연결은 평범한 코딩으로 하고, 안내 블록이 AI에게 `icons.md`와 `logo.md`를 따르게 한다. 안내 블록에 한 줄을 더한다.

### 키트에 더하는 것

| 파일 | 하는 일 |
|---|---|
| `shared/assets/icons.cjs` | 아이콘 세트를 프로젝트의 `node_modules`에서, 없으면 `$WS`에 받아 온다. `--find gear`로 세트 안의 이름을 찾고, 개념 목록을 받아 세트마다 SVG를 모은다. 없는 개념, 획 두께, viewBox, 라이선스를 보고한다 |

### 범위와 정한 것

- 2차: 아이콘 세트 비교와 로고 방향. 캐릭터와 일러스트는 3차.
- 2026-11-26 결정: 결과물은 기록과 자산 파일만 남긴다. 로고는 SVG로만 그리고 이미지 생성 도구는 쓰지 않는다. 로고 색은 design-system의 색 결정을 따르고, design-brand는 정하지 않는다.
- 혼자 쓸 수 있다. 기록에 색과 글자 결정이 있으면 그 값으로, 없으면 지금 코드의 모습으로 그린다.
- 명시적 호출만 허용한다.


## 12. design-motion 설계 (2차)

### 존재 이유

움직임은 시간 위에 있다. 스크린샷 한 장이나 "부드럽게 올라온다"는 설명으로는 판단할 수 없다. 여러 요소가 어떤 순서로 겹쳐 움직이는지, 스크롤과 함께 어떻게 따라오는지는 재생해 봐야 안다. 생성형 도구는 움직임 한 가지를 코드로 내놓는다. 다른 안과 나란히 볼 수 없고, 고치면 전체가 다시 바뀐다. CSS로 흉내 낸 시안도 답이 아니다. GSAP의 ease와 타임라인의 겹침, ScrollTrigger의 따라오기, Motion(옛 Framer Motion)의 spring은 CSS와 다르게 움직인다. design-motion은 모션 디자이너의 순서(목적, 안무, 성격, 시간, 트리거, 움직임 줄이기)를 따른다. **프로젝트가 쓰는 실제 라이브러리(GSAP 또는 Motion)로 여러 안을 한 시계에 맞춰 재생하고, 느리게, 한 프레임씩 보며 고르게** 한다.

### 근거로 삼은 작업 방식

- **목적 먼저** (IBM Carbon 모션): 움직임은 생산적(자주 보는 작업 화면, 짧고 조용하게)과 표현적(드문 순간, 주의를 끄는 곳)으로 나뉜다. 들어올 때와 나갈 때 곡선이 다르다. 움직이는 거리와 크기가 클수록 시간이 길어진다.
- **스토리보드, 애니매틱, 프로토타입, 사양 넘김** (Smashing Magazine, Viget, Val Head의 UI 모션 작업 글): 핵심 상태를 먼저 정하고, 시간 정보가 필요하면 움직이는 시안으로 넘어간다. 넘길 때는 대상, 속성(시작과 끝 값), 시간, 곡선, 지연, 도중에 끊길 때의 동작, 움직임 줄이기 판을 적은 사양을 준다.
- **GSAP 사용 수칙** (`greensock/gsap-skills`, MIT): 타임라인으로 순서를 짓고, transform과 opacity만 움직이고, 프레임워크에서는 정리(`gsap.context`, `useGSAP`)를 한다. 가져오는 것은 수칙이고, 문장은 새로 쓴다.
- **Motion 문서** (motion.dev): spring은 시간 대신 물리 값(stiffness와 damping, 또는 체감 시간과 튕김 정도)으로 정해지고, 끝나는 시각은 계산 결과다. 그래서 spring은 시간을 재서 캡션에 적는다.
- **접근성**: `prefers-reduced-motion`에 대응한다. 5초 넘게 저절로 움직이는 것은 멈출 수 있어야 한다(WCAG 2.2.2).

### design-helper, design-system과의 경계

| 요청 | 맡는 스킬 |
|---|---|
| 버튼 hover 전환 시간 150과 200 중에, CSS transition의 easing 하나 | `design-helper` (지금 그대로) |
| 프로젝트 전체의 시간 단계와 easing 토큰 | `design-system`의 모션 영역 |
| 여러 요소가 어떤 순서로 움직이는가, 스크롤과 연동, 요소가 자리를 옮기는 전환(Flip, layout 애니메이션), 글자 쪼개 움직이기, 타임라인과 spring | `design-motion` |
| 프로젝트가 GSAP나 Motion으로 움직이는 요소의 값 하나 | `design-motion`. `design-helper`는 CSS 근사로 그리지 않고 한 줄로 안내한다 |
| three.js | 3차 |

기준은 "CSS 속성 하나의 값인가, 시간 위의 구성인가"다. 앞은 `design-helper`, 뒤는 `design-motion`이다. design-motion은 기록에 시간과 easing 토큰이 있으면 그것을 먼저 쓴다. 토큰 밖의 값은 `새 값`으로 표시한다(새로 만들기 전에 찾는다).

### 흐름: 순간 하나를 큰 것에서 작은 것으로

한 세션은 움직이는 순간 하나(페이지 진입, 목록 등장, 패널 열기, 스크롤 구간 하나)를 다룬다.

| 단계 | 하는 일 | 정하는 방법 |
|---|---|---|
| 1. 순간과 목적 | 어느 순간인가, 무엇을 위해 움직이나(어디서 왔는지 보여 주기, 상태가 바뀌었음을 알리기, 주의 끌기, 표현), 얼마나 자주 보나(생산적인가 표현적인가) | 대화 |
| 2. 지금 움직임 | 지금 코드의 움직임을 재생해 프레임 띠로 보여 준다. 없으면 없다고 한 줄 | 대화, 프레임 띠와 함께 |
| 3. 안무 | 무엇이 어떤 순서로 움직이나: 한꺼번에, 차례로(stagger), 이어받기(Flip), 앞의 것이 끝나기 전에 겹쳐 시작 | 시트 |
| 4. 성격 | 곡선 계열: 부드럽게 감속(GSAP `power2.out`), 강하게 감속(`expo.out`), 넘쳤다 돌아옴(`back.out`), 탄성(`elastic.out`). Motion이면 tween 곡선과 spring(튕김 없음, 약간, 많이) | 시트 |
| 5. 시간 | 전체 길이와 차례 간격의 사다리 | 시트 |
| 6. 트리거와 끊김 | 한 번 재생, 스크롤에 붙여 따라오기(scrub), 되감기. 도중에 다시 누르면 이어서, 처음부터, 끝으로 | 시트 |
| 7. 움직임 줄이기 | 줄인 판: 투명도만, 즉시 바뀜, 거리 줄임 | 시트. 건너뛸 수 없다 |

- 3단계의 안무는 2차의 가장 중요한 결정이다. 같은 요소들이 같은 시간에 움직여도 순서가 다르면 다른 움직임이다. CSS 근사로 가장 많이 틀어지는 부분이기도 하다.
- 아직 정하지 않은 단계는 가장 평범하게 고정한다(GSAP는 `power2.out`, Motion은 기본 곡선. 시간 400ms, 한 번 재생). 섹션 설명에 한 번 적는다.
- 7단계는 건너뛸 수 없다. 사용자가 끝내려 하면 줄인 판 하나를 기본으로 그려 보여 주고 확인을 받는다.

### 그리는 것: 한 시계로 재생하는 시안

- **실제 라이브러리로 재생한다.** 각 시안은 프로젝트의 실제 CSS로 만든 보드 페이지(`shared/board.md`)이고, 그 안에서 라이브러리가 움직임을 맡는다. 라이브러리는 프로젝트가 쓰는 것(GSAP 또는 Motion)이다. 프로젝트의 `node_modules`에 있으면 그 버전을, 없으면 `$WS`에 받은 최신 버전을 쓰고 캡션에 버전을 적는다. 둘 다 없으면 1단계에서 한 번 묻고 `구현 방침`에 남긴다. GSAP는 2025년부터 플러그인까지 모두 무료다(Webflow의 표준 무료 라이선스). Motion은 MIT다.
- **React의 `<motion.div>`도 같은 엔진으로 그린다.** 시안은 React 없이 Motion의 `animate()`에 같은 값을 넘긴다. 같은 계산 엔진이라 움직임은 같다. 다만 컴포넌트가 처음 나타날 때와 사라질 때(`AnimatePresence`)의 시점은 흉내이므로 `실물과 다름`에 적는다.
- **라이브러리마다 작은 연결부를 둔다.** 시안 페이지는 `window.dhMotion`에 길이, 시각 이동, 재생, 멈춤, 속도만 내놓는다. GSAP는 타임라인으로, Motion은 `animate()`가 돌려주는 재생 제어로 이 다섯 가지를 채운다. 재생 막대와 측정은 이 연결부만 쓰므로 라이브러리를 모른다. three.js(3차)도 같은 연결부로 붙인다.
- **재생 막대.** 섹션 위의 막대 하나가 섹션의 모든 시안을 같은 프레임에 움직인다: 전체 재생, 속도(1배, 0.5배, 0.25배), 진행 막대를 끌어 한 프레임씩 보기, 반복. 속도는 라이브러리의 재생 속도(GSAP `timeScale`, Motion `speed`)로 바꾸므로 시안 사이의 시간 차이가 그대로 남는다. **1배에서 고르고, 0.25배에서 차이를 본다**는 `design-helper`의 원칙을 따른다.
- **프레임 띠.** 키트가 타임라인을 정해진 시각(0, 100, 200ms...)으로 옮겨 가며 찍은 그림을 시안 아래에 가로로 늘어놓는다. 재생하지 않아도 순서와 겹침을 나란히 비교할 수 있다. 실제 라이브러리가 정한 시각의 화면이므로 다시 그린 그림이 아니다.
- **움직임 그래프.** 대상 요소의 위치와 투명도를 시간에 따라 잰 선을 프레임 띠 위에 함께 그린다. 넘쳤다 돌아오는 곡선이나 겹쳐 시작하는 순서가 선으로 보인다.
- 스크롤 연동(6단계)은 재생 막대 대신 시안 안을 직접 스크롤해 본다. 프레임 띠는 스크롤 위치 단위로 찍는다.

### 재고 판단하는 것

| 항목 | 예 | 구분 |
|---|---|---|
| 끝나는 시각과 거의 끝나는 시각 | `끝 620ms · 90% 도달 380ms` | 측정 |
| 넘침 | 목표를 지나친 거리 `넘침 6px` | 측정 |
| 동시에 움직이는 수 | 가장 많을 때 몇 개가 함께 움직이나 | 측정 |
| 레이아웃을 흔드는 속성 | transform과 opacity 밖의 속성(width, top 등)을 움직이는지 | 측정 |
| 줄인 판 | 줄인 판에서 움직인 거리 `이동 0px` | 측정 |
| 목적과 맞는가 | 자주 보는 순간인데 표현적인 움직임인지, 순서가 시선을 끄는 곳과 맞는지 | 판단 |

정지 화면 검사는 움직임을 못 본다는 한계가 있었다(`shared/core.md`, Verify). design-motion은 타임라인을 시각별로 옮겨 재므로, 위 항목은 실제로 확인한 사실이다. 그래도 "느낌"은 재지 못한다. 그것은 사용자가 1배로 보고 정한다.

### 결과물

- 결정 기록의 `motion-<순간>.md`: 목적과 생산적 또는 표현적, 고른 안무와 성격과 시간과 트리거와 줄인 판, 그리고 **사양 표**(대상, 속성 시작과 끝, 시간 또는 spring 값, 곡선, 시작 시각과 간격, 트리거, 끊길 때, 줄인 판). 프레임 띠 스크린샷과 그 라이브러리의 기준 코드 조각(참고용)을 함께 둔다.
- **완료 조건**: 구현 뒤 같은 측정으로 확인할 수 있는 조건(`끝 700ms 이내`, `줄인 판 이동 0px`, `transform과 opacity만`).
- **코드는 쓰지 않는다.** 프로젝트에 라이브러리가 없으면 설치가 필요하다는 것을 기록의 `구현 방침`에 남기고, 구현은 평범한 코딩으로 한다. 안내 블록이 `motion-*.md`를 따르게 한다.

### 키트에 더하는 것

| 파일 | 하는 일 |
|---|---|
| `shared/assets/motion.js` | 시트 쪽 재생 막대. 섹션 안 모든 시안 iframe의 `window.dhMotion`을 한 시계로 묶어 재생, 속도, 진행 위치, 반복을 맞춘다. 시안 페이지에서 GSAP 타임라인이나 Motion 재생 제어를 연결부로 감싸는 작은 도우미(`dhMotion.gsap(tl)`, `dhMotion.motion(controls)`)도 같은 파일에 둔다 |
| `shared/assets/motion.cjs` | Playwright로 시안 페이지를 열고 연결부로 시각을 옮기며 프레임 띠를 찍는다. 대상 요소의 위치, 크기, 투명도를 기록해 그래프(SVG)와 측정값을 낸다. 줄인 판(`prefers-reduced-motion`)으로도 한 번 잰다 |

### 범위와 정한 것

- 2차: GSAP(코어, 타임라인, ScrollTrigger, Flip, SplitText)와 Motion(`animate()`, spring, stagger, 스크롤, layout 애니메이션). three.js는 3차.
- 결과물은 기록과 자산만 남긴다(2026-11-26 결정). design-brand도 같다.
- 혼자 쓸 수 있다. 기록에 모션 토큰이 있으면 그 값을 먼저 쓴다.
- 명시적 호출만 허용한다.

### 2차 시험에서 바뀐 것

2026-11-26에 예제 프로젝트(메모 앱, lucide-react와 GSAP)에서 서브에이전트를 worker로 두고 두 스킬을 한 번씩 돌렸다. 브랜드는 아이콘 세트 고르기와 로고 형식 시트까지, 모션은 안무 고르기, 끝내기 요청, 움직임 줄이기 고르기, 정리까지 갔다. 기록된 문제 62개 중 지침과 키트에 반영한 것은 아래와 같다.

- 키트: 내려받는 파일은 작업 폴더 안에 둔다. 아이콘 이름 찾기는 정확히 같은 이름을 먼저 보여 준다. 프로젝트에 설치가 없으면 `package.json`의 버전 범위를 따른다. Material 아이콘은 글자색을 따르고 획 두께를 보고한다.
- 키트: `pixel.cjs`에 `--color`, `--lang`을 더했다. `check.cjs`는 보드 크기(`boards`), 값이 나온 iframe(`from`), 아이콘 대비(`graphic`), 상자 위치(`box`)를 보고하고, 모션 시트의 재생 막대가 준비될 때까지 기다린다.
- 키트: 모션 시안은 끝 상태에서 쉬고, 자동화된 브라우저에서는 저절로 재생하지 않는다. 그래서 기록용 스크린샷이 비지 않는다. `motion.cjs`는 요소별 시작 시각과 분산(`starts`, `spread`)을 재고, 그래프에 범례를 넣고, 끝을 지난 프레임을 표시한다. 안무를 구분하는 값은 "동시에 움직인 수"가 아니라 시작 분산이었다.
- 지침: `A 지금`은 코드 값을 그대로 쓰고 다른 점을 캡션에 적는다. 고정값에 간격 60ms와 이동 거리를 더했다. 모션 시안은 움직이는 영역만 잘라 520px 이하로 둔다.
- 지침: 대화로 정하는 단계를 답하지 않고 고르면, 그 단계는 `초안`으로 두고 다시 묻는다. 성격 낱말처럼 코드에 없는 것은 묻고, 지침의 예시에서 가져오지 않는다.
- 지침: 마지막 턴에 기록 지시가 작업 폴더의 스크린샷을 가리키면 폴더를 남기고 `정리 지시:`의 `작업 폴더:`로 넘긴다. 메인은 기록을 쓴 뒤 지운다. 기록 지시 안의 코드는 HTML 이스케이프하지 않는다.
- 지침: 로고 시안은 파일 세 개(전체, 심볼, 작은 판)를 늘 쓰고, 반전 자리는 프로젝트에 어두운 면이 없어도 늘 그린다. 본문 서체에 파일이 없으면 Pretendard나 Inter를 대신 쓰고 그렇다고 적는다.
