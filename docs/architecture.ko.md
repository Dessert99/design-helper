# design-helper 스킬 패밀리 설계

상태: 0단계(구조 개편) 완료, 1차(`design-system`, `design-sync`) 초안 구현. 1.5차 이후는 설계안. 2026-11-21 작성, 2026-11-25 갱신.

이 문서는 design-helper를 한 축 비교 도구에서 "디자인 결정을 하나씩 내리게 돕는 스킬 묶음"으로 넓히는 설계다. 구현은 이 문서를 기준으로 하고, 구현 중 바뀐 결정은 이 문서에 먼저 반영한다.

## 1. 이 스킬 묶음이 있어야 하는 이유

### 풀려는 문제

- 디자이너가 아니면 웹페이지 디자인을 어디서부터 정해야 하는지 모른다. 기존 디자인 시스템이 있어도, 새로 시작해도 같다.
- 생성형 디자인 도구(Claude Design 등)는 한 번에 완성된 화면이나 시스템을 내놓는다. 왜 그런 모습인지 알 수 없고, 한 부분을 고치려 하면 다른 부분까지 다시 바뀐다. 그래서 단계적으로 설정하거나 디테일하게 다듬기 어렵다.
- 말로 고르게 하면 판단이 틀린다. "12px이 나을까요, 16px이 나을까요"는 질문이 아니다. 보고 골라야 한다.

### 우리의 답: 결정 루프

모든 스킬은 같은 루프를 돈다. 이 루프가 우리 스킬의 정체성이다.

```
① 결정 하나를 정한다        (값 하나, 규칙 하나, 방향 하나, 패턴 하나)
② 실제 맥락 위에 그린다      (프로젝트 코드, 실제 콘텐츠, 이미 정한 것)
③ 나란히 놓고 차이에 이름을 붙인다
④ 사용자가 눈으로 고른다     (채팅으로, 추천은 근거와 함께 아래에)
⑤ 근거와 함께 기록한다
⑥ 고른 것 위에 다음 결정을 쌓는다
⑦ 반영은 고른 뒤에만 한다    (코드 또는 결정 문서)
```

생성형 도구는 ①~⑥을 건너뛰고 ⑦의 결과물을 한 번에 만든다. 우리는 결과물을 만드는 속도가 아니라, 결과물 안의 결정 하나하나를 사용자가 내리게 하는 데 가치를 둔다.

### 불변 원칙

모든 스킬이 지킨다. 어떤 스킬의 지침이 이 원칙과 부딪히면 지침을 고친다. 원칙에 예외를 만들지 않는다.

| 번호 | 원칙 | 어기는 예 |
|---|---|---|
| P1 | 그려서 보여 준다 | 시안을 산문, 표, ASCII로 설명하고 고르게 한다 |
| P2 | 한 번에 결정 하나 | 로고와 색과 서체를 한 시안 묶음에서 함께 바꾼다 |
| P3 | 차이에 이름을 붙인다 | "A: 모던", "B: 미니멀"처럼 무엇이 다른지 없는 룩 모음(프리셋 갤러리) |
| P4 | 실제 맥락 위에서 그린다 | lorem ipsum, 회색 상자, 실제 화면과 동떨어진 단독 시안 |
| P5 | 결정은 사용자가 한다. 확정은 시안으로 본 것만 | 추천을 시안 위에 두거나, 고르기 전에 하나로 좁힌다. 말로만 들은 값을 확정으로 기록한다 |
| P6 | 보는 것과 반영을 나눈다 | 고르기 전에 프로젝트 코드나 문서를 바꾼다 |
| P7 | 기록이 다음의 기준이다 | 앞에서 정한 값을 무시하고 다음 시안을 그린다 |

P2의 "결정 하나"는 스킬마다 단위가 다르다(2장). 값 하나일 수도, 규칙 하나일 수도, 방향 하나일 수도 있다. 다만 한 시안 묶음 안에서 움직이는 것은 그 하나뿐이고, 그 하나에 이름이 붙어 있어야 한다.

제안의 범위도 스킬마다 다르다. design-helper는 기존 범위를 재는 자로 남고 지어내지 않는다. 나머지 스킬은 안을 제안한다. 하지만 제안하는 스킬도 P2와 P3를 지키므로, 결과는 언제나 "이름 붙은 차이 몇 개 중 하나를 고르는 일"이 된다.

## 2. 스킬별 존재 이유

각 스킬은 "생성형 도구로는 왜 안 되는가"에 답해야 한다. 이 답이 각 `SKILL.md`의 첫 문단이 된다. 답하지 못하는 기능은 만들지 않는다.

| 스킬 | 풀려는 문제 | 결정 단위 | 그리는 것 | 결과물 | 자동 실행 |
|---|---|---|---|---|---|
| `design-helper` | 값 하나를 숫자로는 판단할 수 없다 | 축 하나의 값 | 기존 컴포넌트에 값만 바꾼 사다리 | 코드 반영 | 허용 |
| `design-system` | 어디서 시작할지 모르고, 정할 것이 너무 많다 | 체크리스트 항목 하나 (값보다 규칙) | 대표 화면 보드에 규칙 하나를 바꿔 적용 | 결정 문서 (체크리스트) | 명시적 호출만 |
| `design-sync` | 생성형 도구는 디자인이 바뀌면 화면을 통째로 다시 만든다. 무엇이 바뀌는지 모른 채 받아들이게 된다 | 동기화 범위 하나 (전체, 영역, 항목) | 대표 화면을 지금과 동기화 후로 나란히, 바뀌는 토큰과 영향 범위 | 코드 반영, 프로젝트의 AI 안내 블록 | 명시적 호출만 |
| `design-ux` | UX는 흐름과 동작이라 정지 화면이나 설명으로 판단할 수 없고, 생성형 도구는 한 가지 UX만 낸다 | 패턴 하나 (내비게이션 방식, 입력 흐름, 빈 상태 처리 등) | 실제 콘텐츠로 동작하는 HTML 시안. 같은 과제를 각 안에서 직접 해 보게 한다 | 결정 문서 | 명시적 호출만 |
| `design-motion` | 움직임은 스크린샷이나 설명으로 판단할 수 없고, CSS 근사는 GSAP나 three.js와 다르게 움직인다 | 파라미터 하나 또는 방향 하나 | 실제 라이브러리로 동시에 재생하고 느리게도 보는 시안 | 결정 문서 또는 코드 반영 | 명시적 호출만 |
| `design-brand` | 로고, 아이콘, 캐릭터를 단독 완성품으로 받으면 실제 화면에서 어떻게 보일지 모른다 | 속성 이름이 붙은 방향 하나 | 실제 쓰이는 자리(헤더, 16px 파비콘, 버튼 속 아이콘, 빈 상태 그림)에 입힌 시안 | 결정 문서와 자산 파일 | 명시적 호출만 |

CSS로 할 수 있는 값 하나의 모션(시간, easing)은 지금처럼 `design-helper`가 맡는다. `design-motion`은 라이브러리가 필요한 모션과 3D를 맡는다.

### 스킬 사이의 관계

```
design-system ──(체크리스트와 기초 규칙)──┐
design-ux ────(패턴 결정)────────────────┤
design-brand ─(방향과 자산)───────────────┼──▶ 결정 문서 ──▶ design-helper가 제약으로 읽고
design-motion ─(모션 결정)────────────────┘                    값 하나씩 코드에 반영
                                                  │
                                                  └──▶ design-sync가 확정된 것만 코드에 동기화하고,
                                                       프로젝트의 AGENTS.md와 CLAUDE.md에 안내 블록을 넣음
```

결정 문서가 스킬 사이의 공용 상태다. 어느 스킬이든 문서가 있으면 먼저 읽고, 이미 정한 것 위에 그린다(P7).

## 3. 공통 구조

### 역할 나눔

지금 구조를 그대로 쓴다.

- 메인 에이전트는 스킬의 `SKILL.md`와 `shared/main.md`만 읽는다. 사용자와 worker 사이에서 말을 전하고, 프로젝트와 외부에 쓰는 일을 전부 맡는다.
- worker는 코드를 읽고, 시트를 그리고, 검증한다. 프로젝트 파일과 외부 문서에는 쓰지 않는다. 쓸 것은 블록으로 넘긴다.

### 넘김 블록

worker가 메인에게 넘기는 블록은 세 가지다. 사용자에게는 보이지 않는다.

| 블록 | 언제 | 메인이 하는 일 |
|---|---|---|
| `반영 지시:` | 코드에 반영할 선택을 했을 때 | 코드를 고치고 검증한다 |
| `기록 지시:` | 문서에 기록할 선택을 했을 때 (새로 추가) | 결정 문서에 항목을 쓰고, 스크린샷을 함께 저장한다 |
| `정리 지시:` | 끝날 때 프로젝트에 비교 파일이 남았을 때 | 이번 세션이 만든 근거가 있는 파일만 지운다 |

### 결정 문서

결정 문서의 틀은 Astryx(`meta/astryx`, MIT)가 AI에게 디자인 시스템을 다루게 하는 방식에서 가져온다. 가져오는 것은 틀뿐이다. 문서 구조, 결정 상태, 의도와 값의 분리, 역할로 정리하기, 결정 기록, 다시 볼 조건, 검증 칸이 여기에 해당한다. Astryx의 값, 토큰 이름, 컴포넌트는 가져오지 않는다. 그 값을 쓰고 싶으면 가져오기 출처에서 기반으로 고른다. 문장은 우리 말로 새로 쓰고, README에 참고 출처를 밝힌다.

**위치**

- 사용자가 노션 링크를 주면 그 아래에 같은 구조의 상위, 하위 페이지로 쓴다.
- 언급이 없으면 프로젝트의 `design-decisions/`에 쓴다.
- 노션 링크를 받았는데 노션 도구가 없으면 `design-decisions/`에 쓰고, 그 사실을 한 줄로 알린다.

**구조: 영역마다 파일 하나**

```
design-decisions/
├─ README.md          기반 시스템, 체크리스트 진행 상황, 목차
├─ typography.md      글자
├─ color.md           색
├─ spacing.md         간격과 밀도
├─ shape.md           모서리, 테두리, 그림자
├─ ux-<패턴>.md        UX 결정은 패턴마다 한 파일
└─ assets/            결정의 근거가 된 시트 스크린샷
```

영역을 나누면 한 영역만 다시 정할 때 그 파일만 읽으면 된다. 전체 진행 상황은 `README.md`의 체크리스트 한 곳에서 본다.

**기록 하나의 양식** (`shared/decisions.md`에 둔다)

| 칸 | 내용 | 가져온 방법 |
|---|---|---|
| frontmatter `status` | `초안`, `확정`, `보류`, `보관` 중 하나 | 결정 상태 (draft, current, archived) |
| frontmatter `decided` | 확정한 날짜 | 승인 날짜 |
| frontmatter `base` | 이어받은 기반과 버전. 없으면 비운다 | 상속과 덮어쓰기 (`extends`) |
| frontmatter `reopen_when` | 무엇이 바뀌면 이 문서를 다시 봐야 하는가 | 다시 볼 조건 (`review_triggers`) |
| frontmatter `verify` | 이 결정이 지켜지는지 무엇으로 확인하는가 | 검증 방법 (`verified_by`) |
| 의도 | "~해야 한다" 문장. 숫자를 쓰지 않는다. 사용자의 "느낌"이 여기로 온다 | 의도와 값의 분리 (design spec) |
| 역할과 값 | 역할, 토큰, 값(라이트와 다크), 출처(기반 그대로, 시안 글자) | 역할 기반 토큰 |
| 결정 기록 | 번호(D1), 결정한 사람과 날짜, 시트 요청과 시안 글자, 이유, 스크린샷 | 결정 로그 (DEC-n) |
| 스크린샷 설명 | 상태, 모드, 폭, 보여 주는 결정 | 기준 이미지의 맥락 |
| 열린 질문 | 아직 못 정한 것 (Q1). 체크리스트의 보류 항목과 연결한다 | 열린 질문 (OQ-n) |
| 정하지 않는 것 | 이 문서가 다루지 않고 다른 문서에 맡기는 것 | 내용 경계 (Content boundary) |

frontmatter 이름은 에이전트가 안정적으로 읽도록 영어로 쓰고, 값과 본문은 한국어로 쓴다.

**규칙**

1. **확정은 시각 자료를 보고 고른 것만.** 디자인 시스템의 값을 새로 정하든 고치든, 결정은 반드시 시트에 그린 시안을 보고 채팅에서 고른 것이어야 한다. 사용자가 숫자를 직접 말해도(`버튼은 8px로 둥글게`) 그 값을 시트에 그려 보여 주고, 그동안은 `초안`으로 둔다. 비교 대상이 필요하면 현재 값이나 이웃 단계를 함께 그린다. 기반을 고를 때도, 결정을 되돌릴 때도 같다.
2. **확정의 길은 하나다.** 코드에 이미 들어갔다거나 반대가 없었다는 이유로 확정으로 보지 않는다.
3. **바꿀 때는 지우지 않고 보관한다.** 옛 결정은 `보관`으로 남기고 새 결정과 서로 링크한다.
4. **역할 이름의 우선순위.** 프로젝트에 이미 있는 토큰 이름, 사용자가 정한 이름, 스킬의 기본 역할 목록 순서로 쓴다. 기본 목록은 출발점일 뿐이고, 역할을 바꾸거나 더하는 것도 체크리스트 항목이다.
5. **역할 먼저, 값은 나중에.** 영역마다 역할을 먼저 정하고, 역할마다 값을 사다리로 고른다.
6. **문서와 코드가 다르면 문서의 `확정`이 기준이다.** 다른 점은 발견 사항으로 알리고 자동으로 고치지 않는다. 문서가 없는 기존 프로젝트에서 시작할 때는 현재 코드 값을 `초안`으로 불러와 출발점으로 쓴다.
7. **`design-system`은 코드를 고치지 않는다.** 결과물은 결정 문서뿐이다. 코드에 옮기는 일은 사용자가 따로 요청할 때 design-helper로 하나씩, 또는 이후에 만들 적용 단계에서 한다.
8. **design-helper도 문서를 지킨다.** 결정 문서가 있으면 읽고 제약으로 쓴다. 고른 값이 문서에 기록된 역할에 해당하면 `반영 지시:`와 함께 `기록 지시:`도 넘긴다. 문서가 없으면 지금과 같다.
9. **기반은 버전과 함께 기록하고 저절로 따라가지 않는다.** 기반을 바꾸는 것은 새 결정이고, 규칙 1에 따라 시트로 본다.
10. **연쇄 확인.** 결정이 바뀌면 그 변화와 `reopen_when`이 겹치는 다른 문서를 찾아 알린다. 다시 정할 때는 규칙 1에 따라 시트로 보여 준다. 자동으로 고치지 않는다.
11. **측정할 수 있는 것은 측정한다.** 대비, 넘침, 잘림은 직접 확인해 캡션에 적는다. 사용자에게는 취향과 방향만 한 번에 하나씩 묻는다. (`shared/core.md`)
12. **새로 만들기 전에 찾는다.** 새 토큰이나 결정을 제안하기 전에 결정 문서와 프로젝트 토큰을 먼저 찾는다. 새로 만들 때는 기존 것을 못 쓰는 이유를 캡션에 적는다. (`shared/core.md`)
13. **반영 후 자기 점검.** 코드에 반영한 뒤, 바뀐 줄에 결정된 토큰 대신 하드코딩된 색이나 px가 들어갔는지 검사해 보고한다. (`shared/main.md`)

**한 번의 결정이 기록되는 흐름**

```
사용자: "C로 갈게"
  → worker: 기록 지시: (어느 문서의 어느 칸에 무엇을, 스크린샷 경로)
  → 메인: 해당 영역 문서에 결정과 값을 쓰고, 스크린샷을 assets/로 복사하고, README 체크리스트를 갱신
  → 메인: reopen_when이 겹치는 문서를 한 줄로 안내
```

### 가져오기

값을 처음부터 고르는 대신, 공개된 디자인 시스템의 값을 시안 후보로 가져올 수 있다.

- **출처:** Tailwind 기본값, Radix Colors, Open Props, Material 3, shadcn/ui. 값이 공개돼 있고 가져다 써도 되는 라이선스인 것만 둔다. 이 밖의 시스템은 사용자가 이름을 말할 때만 쓰고, 회사의 브랜드 시스템은 값을 참고하는 데만 쓴다.
- **단위:** 항목 하나(간격 기본 단위만), 영역 하나(색 전체), 전체 기반(`base`) 중 고른다. 섞어 써도 된다.
- **가져오는 것:** 디자인 토큰(값과 역할 구분 방식)만 가져온다. UI 컴포넌트는 코드가 아니라 모양의 값(높이, 여백, 모서리)만 후보로 쓴다. 접근성은 가져오는 대상이 아니라 우리가 재는 기준이다.
- 가져온 값도 시안 후보 중 하나다. 지금까지 정한 것이 모두 적용된 보드 위에서 비교하고, 고른 것만 확정한다(규칙 1).

### 접근성

두 층으로 나눈다.

| 층 | 내용 | 다루는 곳 |
|---|---|---|
| 보이는 접근성 | 글자와 배경의 대비, 누르는 영역 크기, 포커스 표시, 색만으로 의미를 전하지 않기, 움직임 줄이기 | `design-system`. 기준은 WCAG 2.2 AA(본문 대비 4.5:1, 큰 글자와 아이콘 3:1, 누르는 영역 약 44px). 직접 재서 캡션에 적고, 기준 미달 시안도 숨기지 않고 표시한다(`대비 부족 2.5:1`). 포커스 표시 모양은 결정 항목 하나로 두고 시안으로 고른다 |
| 동작 접근성 | 키보드 이동, 포커스 가두기, 스크린리더용 정보(ARIA) | 결정 문서의 "구현 방침"으로 기록한다. 프로젝트 스택에 맞는 후보를 제안하고 사용자가 고른다(React면 Radix Primitives나 Base UI, 단순한 화면이면 HTML 기본 요소 우선). 라이브러리 설치와 적용은 코드를 고치는 단계의 일이다 |

### AI가 결정을 따르게 하는 장치

결정 문서를 만들어도 다른 AI 세션이 그것을 모르면 소용이 없다. Astryx(`meta/astryx`)가 AI에게 자기 디자인 시스템을 따르게 하는 방식에서 장치만 빌려 와, 우리 결정 문서에 맞게 새로 쓴다. Astryx의 문서나 값은 가져오지 않는다.

| 장치 | Astryx | 우리 |
|---|---|---|
| 안내문 심기 | `astryx init`이 프로젝트의 `AGENTS.md`, `CLAUDE.md`에 안내 블록을 쓴다 | `design-sync`가 같은 두 파일에 표시 주석으로 감싼 안내 블록을 넣는다. 우리 스킬을 쓰지 않는 평범한 코딩 세션도 결정을 따르게 된다 |
| 추측 대신 확인 | 컴포넌트를 쓰기 전에 CLI로 확인하게 한다 | 화면을 만들기 전에 결정 문서의 해당 영역을 읽게 한다. 확정 값만 쓰고, 정해지지 않은 것은 지어내지 않고 가장 가까운 토큰을 쓴 뒤 알린다 |
| 내기 전 점검 | 하드코딩된 색과 px를 토큰으로 바꾸게 한다 | 같은 점검을 안내 블록에 넣는다 |
| 바꾸는 길 막기 | (해당 없음) | 결정된 값을 코드나 문서에서 직접 바꾸지 못하게 하고, 시안을 거치는 `design-system`으로 안내한다 |

- 이 장치는 결정 문서 양식과 분리해 `shared/agent-guide.md` 한 파일에 둔다. 안내 블록의 원본, 넣고 갱신하는 규칙, 점검 규칙이 여기에 모인다.
- 블록은 표시 주석(`<!-- DESIGN-DECISIONS:START -->`, `END`) 사이만 관리한다. 다시 동기화하면 그 사이만 바뀌고, 사용자가 쓴 나머지는 건드리지 않는다.
- 두 파일은 그 프로젝트의 모든 AI 세션에 영향을 주므로, 처음 넣을 때 한 번 확인을 받는다.
- 동기화로 코드와 문서가 맞춰진 시점에 넣는다. 문서에만 있고 코드에 없는 값을 다른 AI가 먼저 쓰지 않게 하기 위해서다.

### 동기화 (`design-sync`)

```
① 결정 문서에서 확정 항목만 읽음 (초안, 보류는 건너뜀)
② 프로젝트의 스타일 체계를 감지하고 지금 토큰과 비교 (추가, 변경, 같음, 코드에만 있음)
③ 바뀌는 토큰마다 영향 범위 계산
④ 시트에 대표 화면을 지금과 동기화 후로 나란히 그림
⑤ 사용자가 보고 범위를 고름 (전체, 영역, 항목)
⑥ 메인이 코드에 반영하고 검증하고, 하드코딩 값을 점검하고, 안내 블록을 넣거나 갱신
```

- 방향은 문서에서 코드로만 간다. 코드 값을 문서로 가져오는 것은 `design-system`이 처음 시작할 때 초안으로 한다(규칙 6).
- 동기화 중에 코드 값이 낫다고 판단되면 문서를 고쳐야 하고, 그 변경은 `design-system`에서 시안으로 정한다.
- 결과물 형식은 프로젝트의 스타일 체계를 따른다(CSS 변수, Tailwind 테마, SCSS 변수, CSS-in-JS 테마). 감지는 `shared/stylesystems.md`를 쓴다.

### 작업 폴더와 키트

지금과 같다. 시트, 서버, 메모, 스크린샷은 프로젝트 밖의 `$WS`에 둔다. 서버(`serve.py`), 시트(`sheet.html`), 검사(`check.cjs`)는 모든 스킬이 함께 쓴다.

- 스킬 폴더에는 그 스킬의 규칙만 둔다. 두 스킬 이상이 쓰는 규칙은 `shared/`로 올린다. 같은 규칙을 두 곳에 쓰지 않는다.
- 아직 구현하지 않은 스킬은 폴더도 만들지 않는다. 동작하지 않는 명령어가 목록에 보이지 않게 한다.
- `SKILL.md`는 짧게 유지한다. description, 존재 이유 한 문단, worker 파일 경로, `shared/main.md`를 따르라는 지시만 둔다.

## 5. Claude Code와 Codex 양쪽 지원

### 플랫폼별 차이

| 항목 | Claude Code | Codex |
|---|---|---|
| 설치 | `.claude-plugin/plugin.json` | `.codex-plugin/plugin.json`, `"skills": "./skills/"` |
| 명령어 | `/design-helper:design-system` (플러그인 이름이 앞에 붙음) | `$design-system` |
| 자동 실행 끄기 | `SKILL.md` frontmatter `disable-model-invocation: true`. description이 맥락에 아예 들어가지 않는다 | 스킬의 `agents/openai.yaml`에 `policy.allow_implicit_invocation: false` |
| worker 띄우기 | Agent 도구, subagent type `design-helper:worker` | `spawn_agent`, 독립 맥락 (`fork_turns: "none"` 또는 `fork_context: false`) |
| worker에 이어 말하기 | `SendMessage` | `send_input` 또는 `followup_task`, 기다릴 때 `wait_agent`, 끝낼 때 `close_agent` |
| 공용 폴더 경로 | `${CLAUDE_PLUGIN_ROOT}/shared/` (스킬과 에이전트 본문에서 치환됨. `../`는 보장되지 않음) | 스킬 폴더 기준 `../../shared/` (공식 `work-pets` 플러그인과 같은 방식) |
| 스킬 자신의 폴더 | `${CLAUDE_SKILL_DIR}` | 스킬을 불러올 때 주어지는 경로 |
| 이미지 생성 | 없음 | 내장 `image_gen` (`imagegen` 시스템 스킬) |
| 노션 | 연결된 Notion 도구 | 설치된 Notion 플러그인 |
| 패키징 제외 | 없음 | `.codexignore`가 `agents/`, `docs/`, `scripts/`를 뺀다 |

### 양쪽에서 같은 파일이 동작하게 하는 규칙

1. **경로는 두 가지를 함께 적는다.** 예: "공용 파일은 플러그인 최상위의 `shared/`에 있다. Claude Code에서는 `${CLAUDE_PLUGIN_ROOT}/shared/`, Codex에서는 이 스킬 폴더 기준 `../../shared/`다." Codex에서는 변수가 치환되지 않고 글자 그대로 남으므로, 두 번째 경로를 쓰라고 적어 둔다.
2. **도구는 플랫폼 이름보다 능력으로 적는다.** 예: "이미지 생성 도구가 있으면 쓰고, 없으면 SVG로 그리고 그 사실을 시트에 적는다." 플랫폼이 바뀌거나 도구가 늘어도 지침을 고칠 필요가 없다.
3. **도구 이름이 꼭 필요한 곳(worker 띄우기, 이어 말하기)은 `shared/main.md` 한 곳에만 둔다.** 플랫폼 도구가 바뀌면 그 파일만 고친다.
4. **worker 에이전트는 하나다.** Claude Code의 `agents/worker.md`는 첫 메시지로 받은 스킬의 `worker.md` 경로를 읽고 따른다. Codex는 `agents/`를 패키징하지 않으므로, 메인이 처음부터 `worker.md`의 절대 경로를 넘긴다(지금 방식).
5. **새 스킬마다 양쪽 자동 실행 설정을 함께 넣는다.** `disable-model-invocation`과 `agents/openai.yaml`은 짝으로 다닌다. 한쪽만 넣으면 다른 플랫폼에서 무거운 스킬이 자동 실행된다.

### 쓰지 않기로 한 것

- Claude Code의 `context: fork` (스킬을 포크된 서브에이전트로 한 번 실행): 결과를 한 번 받고 끝나서, 여러 라운드 이어지는 비교에 맞지 않는다. 지금처럼 worker를 띄우고 이어 말하는 방식을 유지한다.
- 접두사 없는 Claude Code 명령어(`/design-system`): 문서에서 확인되지 않아 기대하지 않는다. README에는 `/design-helper:design-system`으로 안내한다.

## 6. 잘못된 채택 막기

| 겹 | 장치 |
|---|---|
| 1 | 자동 실행은 `design-helper` 하나만 허용한다. 나머지는 양쪽 플랫폼 모두 명시적 호출로만 실행된다 |
| 2 | `design-helper`의 description에 제외 문구를 넣는다: 디자인 시스템, UX 패턴, 브랜드, 라이브러리 모션 작업에는 쓰지 않는다 |
| 3 | `design-helper`에 그런 요청이 들어오면 혼자 범위를 넓히지 않는다. 맞는 명령어를 한 줄로 안내하고, 지금 할 수 있는 한 축 비교를 제안한다 |
| 4 | 명시적으로 부른 스킬 안에서도 범위가 애매하면 `shared/clarification.md`대로 한 번 묻는다 |

채택 확인용 프롬프트 목록을 `docs/`에 두고, 지침을 바꿀 때마다 기대한 스킬이 채택되는지 손으로 확인한다.

| 프롬프트 | 기대 |
|---|---|
| 카드 그림자 블러 5가지로 보여줘 | `design-helper` |
| 버튼 여백 12랑 16 중에 뭐가 나아 | `design-helper` |
| 디자인 시스템 처음부터 잡고 싶어 | 자동 채택 없음. `design-helper`가 채택되면 `/design-helper:design-system`(Codex는 `$design-system`) 안내 |
| 로고 만들어줘 | 자동 채택 없음 |
| 디자인 문서대로 코드 맞춰줘 | 자동 채택 없음. `design-sync` 안내 |
| 이 버튼 컴포넌트 구현해줘 | 채택 없음 (평범한 코딩) |

## 9. 정해진 것 (1차)

- 기본 체크리스트: 필수는 기반, 글자, 간격, 색, 모양, 구현 방침. 선택은 레이아웃, 모션, 컴포넌트. 필수를 마치면 선택 영역을 이어 갈지 한 번 묻는다. 항목, 기본 역할, 기본 의도, 기본 검사는 `skills/design-system/references/checklist.md`.
