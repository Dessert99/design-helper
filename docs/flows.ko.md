# 사용 흐름 모음

이 문서는 스킬의 일부가 아닙니다. `SKILL.md` 도 `references/` 도 이 파일을 읽지 않고,
작업 중에 참조되지도 않습니다. `design-helper` 가 실제로 어떻게 흘러가는지 적어 둔
것이고, 용도는 하나입니다 — **읽다가 어색한 데가 보이면 절차를 고치는 것.**

표기 — `❯` 사용자가 한 말 · `·` 내가 하는 것 · `⚠︎` 절차가 시험받는 지점

---

## 기본형

### 1. 축이 이미 있는 주문

```
❯ 카드 그림자 블러 5가지로 보여줘
```

- 세션 첫 주문이면 스택 확인 → 프로젝트 밖에 작업 폴더 하나 → 시트 → 서버 → 브라우저 열기
- 블러만 움직인다. A 4px · B 8px · C 12px · D 16px · E 24px, 나머지는 현재 값으로 붙잡음
- 표본마다 캡션 3줄, 사다리 아래 `경계 — D·E 는 이 크기에서 구분이 안 됩니다`
- 내가 새로고침하고 스크린샷까지 본 뒤, 채팅은 두 줄: 어디를 보면 되는지와 이 사다리의 질문

```
❯ C로 갈게
```

- `확정: 그림자 블러 = C 12px` — 이 한 줄 쓰고 멈춤

> ⚠︎ 축이 이미 요청에 있으니 되묻지 않는다. "어떤 배경에서 볼까요" 같은 확인도 없이 그린다.
> ⚠︎ 선택 뒤에 "다음은 농도를 볼까요" 가 붙으면 위반이다. 다음은 사용자가 정한다.

### 2. 축이 없는 주문

```
❯ 버튼 좀 다듬자
```

- 그릴 수 없다. 되묻는다 — `지금 버튼에서 뭐가 걸리나요?`

```
❯ 좀 답답해 보여
```

- `답답한 게 높이인가요, 안쪽 여백인가요, 글자 간격인가요?`

```
❯ 글자가 벽에 붙어 있어
```

- 축이 잡혔다 — 가로 padding. 한 번 더 좁힌다: 세로도 같이 움직일지, 가로만 볼지
- 확정되면 그때 그린다

> ⚠︎ `크기 → 여백 → 모서리 → 색` 을 늘어놓는 순간 메뉴가 된다. 질문은 사용자가 이미
> 느끼는 불만을 좁히는 쪽으로만 간다.
> ⚠︎ 두 번째 대답에서 짐작하고 그리기 시작하면 틀린 축을 다섯 개 그리게 된다.
> ⚠︎ radius·tracking·easing 을 풀어 설명하지 않는다. 그대로 쓴다.

### 3. 연속 주문

```
❯ 이제 모서리 볼까
```

- 그림자 블러는 **확정값 12px 로 붙잡고** 모서리만 움직인다
- 글자는 다시 A 부터. 지난 단위를 가리킬 일이 있으면 `그림자 블러 C` 라고 부른다
- 새 사다리는 시트 맨 아래에 붙고, 브라우저는 스스로 새로고침해서 그 자리로 내려간다

> ⚠︎ 확정값을 안 깔고 그리면 표본이 전부 틀린다. 이게 메모를 유지하는 유일한 이유다.
> ⚠︎ 메모는 화면에 안 나온다. 결정표도, 머리말 확정값 줄도 없다.

### 3-1. 사다리를 사용자가 직접 움직일 때

```
❯ (창 슬라이더를 오른쪽으로 끌었다)
```

- 내 턴은 없다. 일곱 칸이 한 프레임에 같이 다시 그려지고, 문자도 값도 비용칩도 따라 바뀐다
- 내가 써 둔 `경계 —` 줄은 흐려지고 `창을 옮겼습니다. 경계는 다시 봐야 합니다` 가 붙는다
- 다음에 내가 말할 차례가 오면 **흐려진 경계를 먼저 다시 본다.** 새 창에서 computed style
  과 스크린샷을 다시 보고 경계 문장을 새로 쓴다

```
❯ (스케일에 맞춤 체크를 풀고 13px 로 맞췄다)
```

- 13px 칸은 점선이 둘러지고 비용칩이 `--radius-md 고침 (23곳) · 또는 새 토큰` 으로 뒤집힌다
- 여기서 확정이 들어오면, 메모에 값만 적지 않는다. **스케일 밖이라는 사실을 같이 적는다**

> ⚠︎ 창을 옮긴 뒤에도 옛 경계 문장을 그대로 두고 보고하면, 사용자는 내가 확인한 줄 안다.
> ⚠︎ 슬라이더가 붙었다고 축을 하나 더 얹으면 안 된다. 컨트롤은 주문받은 축의 창과 맥락만 움직인다.
> ⚠︎ 표본 캡션을 문자에 묶어 쓰면(`E 는 …`) 스크럽 한 번에 전부 거짓말이 된다. 값으로 쓴다.

### 3-2. 사용자가 시트에서 확정을 눌렀을 때

- 채팅엔 아무 말이 없을 수 있다. **턴을 시작할 때 `state.jsonl` 을 먼저 읽는다**
- `kind: "choice"` 면 그건 `C로 갈게` 와 같다. 되묻지 않고 한 줄 기록하고 멈춘다
- 기록에는 값만이 아니라 **어떤 맥락에서 골랐는지도 같이 들어 있다** — 배경, 반복, 크기,
  그때의 창. 나중에 그 결정을 다시 볼 때 이게 근거가 된다

> ⚠︎ 이미 처리한 줄을 다시 처리하면 결정이 두 번 기록된다. 파일은 큐가 아니라 증거다.
> ⚠︎ 아무 줄도 없는 걸 "아직 안 골랐다" 가 아니라 "괜찮다는 뜻" 으로 읽으면 안 된다.

## 응답 세 가지

### 4. 인상 — 선택이 아니다

```
❯ C 괜찮네
```

- 확정하지 않는다. 기록도 하지 않는다. 코드는 더더욱 건드리지 않는다
- `C 로 확정할까요, 아니면 그 근처를 더 볼까요?`

> ⚠︎ `괜찮네` 를 확정으로 읽고 다음으로 넘어가는 게 가장 흔한 사고다.

### 5. 보완 — 같은 단위 안에서

```
❯ C가 나은데 좀 더 퍼졌으면 좋겠어
```

- 같은 작업 단위다. 새 단위가 아니다
- C 를 가운데 두고 퍼짐만 움직이는 사다리를 **아래에 덧붙인다.** 글자는 D·E·F 로 이어짐
- 위의 A~E 는 지우지 않는다. 비교 대상으로 남아 있어야 한다

> ⚠︎ 여기서 글자를 A 로 되돌리면 `D로 갈게` 가 어느 표본인지 사라진다.

### 6. 되돌아가기

```
❯ 아까 그림자 블러, 12px 말고 8px이 맞는 것 같아
```

- 메모의 그 줄을 덮어쓴다 — `그림자 블러 = B 8px (C에서 변경)`
- 그 뒤에 확정한 값들이 8px 위에서도 유지되는지는 **눈으로 봐야 안다.** 다시 그려서 보여준다
- 옛 표본은 그대로 둔다

> ⚠︎ 되돌아간 뒤 "그럼 모서리도 다시 볼까요" 로 번지지 않는다. 다시 볼지는 사용자가 정한다.

## 대상별

### 7. 모션

```
❯ 드롭다운 열리는 속도 보여줘
```

- 사다리는 80 · 120 · 160 · 200 · 300ms
- 시트 맨 위에 `전체 재생` 버튼 하나 — 다섯 개가 같은 프레임에 시작해야 비교가 된다
- `1x / 0.25x` 토글. **1x 로 정하고 0.25x 로 구분한다**
- 스크린샷으로는 확인이 안 된다. 그렇다고 말하고, 판단은 사용자 눈에 맡긴다

> ⚠︎ 검증 3단계 중 스크린샷이 무력한 유일한 경우다. 확인한 척하면 안 된다.
> ⚠︎ 프로젝트가 Framer Motion 이면 여기서 정한 cubic-bezier 는 그대로 못 옮긴다.
> 반영 단계가 아니라 **지금** 말해 둔다.

### 7-1. 백지 — 화면에 아무것도 없을 때

```
❯ 버튼 만들어야 하는데 아직 아무것도 없어
```

- 캐물을 게 없다. 불만이 없으니 좁힐 대상이 없다. `어떤 느낌 원하세요?` 는 일을 되던지는 것이다
- 3×3 좌표 스윕을 편다. 가로 `모서리 — 각짐 → 둥글`, 세로 `무게 — 가벼움 → 무거움`
- **가장자리에 축 이름을 쓰고, 그 방향이 어떤 속성을 묶었는지 캡션에 적는다**

```
❯ 무게 말고 밀도로 봐줘
```

- 좌표계를 통째로 갈아서 다시 편다. 이 말이 나올 수 있게 만드는 게 라벨의 목적이다

```
❯ E 에서 시작하자
```

- `출발점: 버튼 = E · 무게 중간 · 모서리 중간 (묶인 속성 전부 미해결)`
- `확정:` 이 아니다. 무엇이 좋게 만들었는지 아직 모른다
- **여기서 백지는 끝난다.** 다음 주문부터는 출발점 위에 평범한 단일축 사다리다

> ⚠︎ 아홉 칸에 축 라벨이 없으면 그건 프리셋 갤러리다. `더 오른쪽` 이 말이 안 되면 실패다.
> ⚠︎ 매트릭스를 모드로 만들면 안 된다. 대상 하나에 한 번 쓰고 사라진다.
> ⚠︎ 코드에 지금 값이 있는데 방향만 바꾸는 거라면, 그 값을 정중앙 칸에 놓고 여덟 칸을 펼친다.

### 8. 구조 · 와이어프레임

```
❯ 이 페이지 사이드바를 왼쪽에 둘지 오른쪽에 둘지 모르겠어
```

- 무채색만. 색·타이포·그림자·라운드 전부 끔. 스킨이 있으면 스킨이 판단된다
- 블록에 역할을 적는다 — `네비` `사이드바` `본문`. 로렘 입숨은 안 쓴다
- 폭이 질문이면 실제 브레이크포인트로 그린다

> ⚠︎ 구조를 정하는 자리에서 "색도 같이 볼까요" 가 나오면 두 축이 섞인다.

### 9. 상태 — hover · focus · disabled

```
❯ 버튼 hover 색 좀 보자
```

- 두 줄로 그린다. `실물` (마우스로 직접 올려 보는 것) 과 `강제 상태` (클래스로 고정해 나란히)
- hover 는 한 번에 하나만 걸리니까 강제 상태 행이 없으면 비교 자체가 안 된다

> ⚠︎ 포커스 트랩·키보드·스크린리더는 여기서 확인 못 한다. 모양과 전환만 정할 수 있다.

### 10. 배경이 조건일 때

```
❯ 황혼 배경에 어울리는 카드를 만들고 싶어
```

- 배경은 변수가 아니라 조건이다. 흰색/회색 기본 배경으로 돌아가지 않는다
- "황혼" 은 한 값이 아니다 — 해 지기 직전 주황 / 푸른 시간대 / 해 넘어간 뒤 남보라 2~3점에 같은 사다리를 얹는다
- 조건이 축을 갈아치운다. 어두운 배경에서 drop-shadow 는 거의 아무 일도 안 하므로,
  그 자리는 glow 나 면 밝기나 테두리 광도가 된다

> ⚠︎ 여기서도 "방향 세 가지를 먼저 잡죠" 는 제안이다. 사용자가 무엇부터 볼지 말해야 그린다.
> ⚠︎ 축을 갈아치운 건 제안이 아니라 사실 보고다 — 그림자를 그려도 안 보인다는 건 측정의 문제다.

### 11. 두 축이 얽힐 때

```
❯ 테두리 두께랑 밝기 같이 봐야 할 것 같은데
```

- 행이 한 축, 열이 다른 축인 매트릭스. 가장자리에 둘 다 라벨
- 3×3 이나 3×4 에서 멈춘다. 5×5 는 눈으로 못 읽는다
- 선택은 칸 하나 — `B3`

> ⚠︎ 두 축을 한 줄로 늘어놓으면(두께와 밝기를 같이 올리는 5개) 어느 쪽이 효과인지 못 가린다.
> 매트릭스는 이 규칙의 예외가 아니라 이 규칙을 지키는 방법이다.

## 스택별

### 12. 무엇으로 그리느냐가 갈리는 지점

시작할 때 한 번 탐지하고, 결과에 따라 그리는 법과 blast radius 가 달라진다.
**무엇으로 그렸는지는 항상 말한다** — 화면만 봐서는 구분이 안 되기 때문이다.

- **Tailwind** — 프로젝트 config 그대로 CSS 를 작업 폴더에 빌드해 유틸리티 클래스로 그린다.
  워처를 같이 돌리지 않으면 새로 쓴 클래스가 조용히 안 나온다. 시트가 프로젝트 밖에 있어서
  `content` 스캔에 안 잡히는데, 이건 CLI 플래그(v3)나 작업 폴더 안의 진입 CSS(v4)로 푼다.
  **프로젝트 안에 config 를 하나 더 만들지 않는다** — 그게 남는 파일이다.
  blast radius 는 클래스 사용처 + 뒤의 토큰
  - v4 는 CLI 가 대개 설치돼 있지 않다(`@tailwindcss/postcss` 로만 빌드한다). npx 가
    받아오는데, **버전을 프로젝트 것으로 고정하지 않으면 앱과 다른 Tailwind 로 그린다**
  - 값이 아니라 클래스를 갈아끼우므로, 표본 안의 **컴포넌트 노드를 `target` 으로 표시**해야
    한다. 맥락 블록이 여러 개라 래퍼에 붙이면 아무 데도 안 닿는다
- **CSS 변수** — 토큰 파일을 `<link>` 걸고 `var(--x)` 로 그린다. 새로고침만으로 반영된다.
  `--radius-card: var(--radius-md)` 같은 사슬을 놓치면 숫자가 틀린다
- **SCSS · CSS-in-JS** — 브라우저가 못 읽는다. 값을 읽어 와 시트 안에 CSS 변수로 옮겨 그린다.
  `theme[key]` 처럼 변수로 접근하는 곳은 grep 이 안 되니, 못 센다고 말한다
- **백지** — 값을 그대로 쓴다. 조용히 실패할 이름이 없으니 이름 확인 단계는 건너뛴다

> ⚠︎ "우리 것 안에서 볼까, 백지에서 볼까" 가 애매하면 한 줄로 묻는다. 이건 메뉴가 아니라
> 측정 조건이다.

## 곤란한 경우

### 13. 그리다 뭔가 발견했을 때

두 가지를 다르게 다룬다.

- **화면에서 실제로 깨진 것** — 말한다. 표본을 잘못 읽게 만드니 측정의 일부다
  `아이콘 칩이 사라졌습니다 — 카드 면 #202020 과 Δ2 입니다`
- **그 밖의 발견** — 한 줄, 한 번, 그걸로 끝. 토큰 이름이 뒤바뀐 것 같다거나, 여기 축이
  하나 더 있어 보인다거나. 그리지 않고, 제안으로 부풀리지 않고, 두 번 꺼내지 않는다

> ⚠︎ 발견은 주문이 아니다. "그래서 이것도 그려 봤습니다" 가 붙는 순간 내가 끌고 가는 것이다.

### 14. 반영

```
❯ 이제 코드에 넣자
```

- **주문받고 시작한다.** 결정 하나 끝날 때마다 "반영할까요" 를 붙이지 않는다
- 진짜 blast radius 를 낸다 — 파일, 줄, 토큰, 같이 움직이는 것
- 그리고 이 질문을 한다: **토큰을 고칠까요, 여기만 덮을까요?** 토큰 수정은 싼 편집이고 비싼 결정이다
- 반영해도 끝이 아니다. 실제 코드에서 확인하고 `됐어` 라고 할 때까지 시트와 브라우저를 붙잡고 있는다
- 끝나면 명령 하나로 서버·워처를 내리고 작업 폴더째 지운다. `git status` 에 내가 만든 게
  하나도 안 보여야 한다. 사용자가 치울 게 있어서는 안 된다

> ⚠︎ 지나가며 언급만 된 대안은 결정이 아니다. 명시적으로 고른 것만 코드에 들어간다.

### 15. 서버가 죽어 있을 때

세션은 살아 있는데 서버가 없는 경우가 생긴다. 탭을 오래 닫아 두면 서버가 스스로 죽기 때문이다.

- **시트를 고치기 전에 살아 있는지 확인하고, 없으면 같은 작업 폴더 위에 다시 띄운다**
- 메모도 `state.jsonl` 도 그대로 남아 있다. 서버만 없어진 것이라 이어서 하면 된다

`python3` 자체가 없으면 서버를 못 띄운다. 이건 다른 얘기다.

- 시트를 `file://` 로 열고, 새로고침은 수동이라고 **한 번** 말하고 진행한다
- 자동 새로고침도 `이걸로 확정` 기록도 안 된다. 선택은 채팅으로 돌아온다
- 우회로를 만들지 않는다

> ⚠︎ 매 턴 "새로고침하세요" 로 끝나면 이 스킬을 쓰는 의미가 반쯤 사라진다.
> ⚠︎ 서버가 죽은 걸 모르고 시트만 고치면, 사용자 화면은 옛날 것을 계속 보고 있다.

### 16. 중간에 그만둘 때

```
❯ 오늘은 여기까지
```

- 정해진 것까지만 메모에 남기고 멈춘다. 코드에는 아무것도 안 들어간다
- 다시 시작하면 그 메모 위에서 이어 그린다. 시트는 하나, 대상 하나

> ⚠︎ "여기까지 온 김에 반영해 둘까요" 는 반영을 제안하는 것이다.

### 16-1. 아무 말 없이 세션이 끝났을 때

터미널을 닫았거나, 크래시났거나, 그냥 자리를 떴다. 종료 명령은 영원히 안 돈다.

- 내가 할 일은 없다. **서버가 스스로 치운다** — 열린 탭이 없으면 10분 뒤 작업 폴더의 모든
  프로세스를 내리고 자기도 죽는다
- 파일은 남긴다. 탭을 실수로 닫은 것과 세션이 끝난 것을 서버는 구분 못 하고,
  메모를 날리는 쪽이 훨씬 나쁘다. 임시 폴더라 OS 가 알아서 회수한다

> ⚠︎ 이게 없으면 버린 세션마다 서버가 포트를 문 채로 하나씩 쌓인다.
> ⚠︎ 신호를 안 넘기는 래퍼로 띄운 워처는 살아남을 수 있다. 이것만은 보장 못 한다.

### 17. 다섯 칸이 똑같이 보일 때

- **에러가 안 난다.** 값이 표본까지 도달 못 했는데 화면은 멀쩡해 보인다.
  클래스를 컴포넌트가 아니라 래퍼에 붙였거나, 토큰 이름이 틀렸거나
- 검증 2단계가 이걸 잡는 유일한 장치다. 값 하나를 읽는 게 아니라
  **칸들을 가로질러 읽고 서로 다른지 확인한다**
- 못 잡고 넘어가면 사용자는 똑같은 걸 다섯 개 놓고 고르게 된다

> ⚠︎ 스크린샷만 보고 "잘 나왔습니다" 하면 이 실패는 통과한다. 작은 차이는 그림으로 구분이 안 된다.
